## 1 The move

- `controller/exchange` → `client/exchange`, `controller/handshake` →
  `client/handshake`, `controller/interaction` → `client/interaction`,
  `controller/peer` → `client/peer`. `git mv` per package (history
  follows), then the package's own imports, then every importer (116
  non-test files plus tests: `grep -rl 'go-fabric/controller/\(exchange\|handshake\|interaction\|peer\)"'`).
  Test packages and `testdata` move with their package.
- `controller/client`, `controller/commissioner`, `controller/ca`,
  `controller/dcl`, `controller/attestation`, `controller/ble`,
  `controller/discovery` and the rest of `controller/` stay: they are the
  role.
- `script/archcheck/layers.json`: `client/...` gets its place so that
  `binding → client/*` and `node → client/*` are ordinary downward edges;
  the four `binding → controller/*` exceptions are removed. No new
  exception. Read `script/archcheck/doc.go` for how layers are assigned
  and keep the layer names.

## 2 The old paths stay for the window (README §API stability)

Each old package becomes a forwarding package, generated by a script
(`script/bx4-forward/` or a scratchpad script kept in the report), not
written by hand: package doc with `Deprecated: moved to
github.com/SukramJ/go-fabric/client/<name> (brief BX4, v0.10.0);
removable in v0.12.0.`, then for every exported identifier of the new
package: a type alias (`type Manager = exchange.Manager`), a function
variable or wrapper (`var NewManager = exchange.NewManager` where the
signature has no type parameters; a wrapper function otherwise), a
constant (`const X = exchange.X`) and a variable (`var ErrFoo = exchange.ErrFoo`
— note: a `var` alias of an error sentinel is the same value, `errors.Is`
holds). Methods need nothing (they travel with the alias). A test that
the forwarding packages compile and that every exported identifier of
the new package has its forward (reflection over `go/doc` or a `go list
-json` diff) — the script's own test. Removal of the forwards is
BV/gate 2's `apidiff` business; name the release in the CHANGELOG.

## 3 The controller's client view (G1-12 second part; P12)

`controller/client → device`, `endpoint` (inventory §1b): read what is
used. If it is the client's view of device types or endpoint numbers,
`schema` (generated from the snapshot) is the right source and the
import moves there; if it is a real dependency on the device layer, say
why in the report and leave it for gate 2. No change to `device/` or
`endpoint/` in this wave.
