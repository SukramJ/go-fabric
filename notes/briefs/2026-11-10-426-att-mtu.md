## Finding (verified 2026-11-10)

`controller/ble.segmentSizeFor` (controller/ble/channel.go:243-275) waits up to `ATTMTUSettleTimeout`
(2 s, :38) for a connection whose `ATTMTU()` is 0 **and** that implements `ble.MTUExchange`
(central.go:54-62: `ATTMTUExchanged() <-chan struct{}`) — matter.js `attMtuOf`
(`packages/nodejs-ble/src/NobleBleChannel.ts:40-41`, `:520-562` at db021da0: noble leaves
`Peripheral.mtu` null until the "mtu" event; the wait keeps the session off the 20-byte minimum).
Only `controller/ble/bletest` implements it (bletest.go:442-446).

**BlueZ.** The `MTU` property of `org.bluez.GattCharacteristic1` exists since **5.62**
(`1abf1400f` doc, `aaa0c4996` getter: `bt_att_get_mtu(att)`, i.e. the *current* ATT MTU — 23,
`BT_ATT_DEFAULT_LE_MTU`, before an exchange; at 5.88 `src/gatt-client.c:909-923`, and since 5.63
the property is omitted while not connected, `aa361e221`). `3a6b5f5ec` (5.62) registers
`att_exchange` per characteristic (`bt_att_register_exchange` in `characteristic_create`) and emits
`PropertiesChanged("MTU")` on the characteristic's path when an exchange completes. Order on connect:
`gatt_client_init` (`src/shared/gatt-client.c:2136-2167`) runs `bt_gatt_exchange_mtu` **first**,
`exchange_mtu_cb` (:1621-1659) then `discover_all`; the D-Bus characteristic objects are created
after discovery, so the `MTU` property read when C1 appears (central_linux.go:536-542) already holds
the negotiated value in the normal case. A value of **23** is ambiguous: the exchange not done (no
exchange when BlueZ's configured MTU is the default, :2161-2163; or a peripheral-initiated exchange
still to come) or the peer's true maximum. Our code today takes 23 as known (`mtu > 0`) and sizes the
segment at the minimum for the session's life — the case the wait exists for.

**ESPHome.** `BluetoothDeviceConnectionResponse.MTU` arrives with the connect answer
(ble/esphome/proxy.go:580-589, wire/proto.go:613; gatt.go:233-236 cites
`bluetooth_connection_bluedroid.cpp:715-733`: the negotiated value, or 23 when the exchange failed).
The MTU is known synchronously; no wait is needed and no `MTUExchange` is implemented.

## Scope

### §1 `ble/bluez`: `connection` implements `ble.MTUExchange`
- Fields: `mtuExchanged chan struct{}` (closed once), `mtuKnown bool`. At C1 discovery
  (central_linux.go:536-542): property absent → `mtu = 0`, **close the channel at once** (BlueZ < 5.62
  cannot report an exchange; the channel waits nothing and the segment is the minimum, as today);
  property > 23 → `mtu = value`, `mtuKnown = true`, close; property == 23 → `mtu = 23`, leave open.
- `handle` (central_linux.go:318-331, `ifaceGattChar`): a `PropertiesChanged` carrying `MTU` for a
  path that is some connection's `c1` (keep a `c1 → conn` map beside `notifying`, or look C1 up under
  `c.mu`) sets `mtu`, `mtuKnown = true` and closes the channel once. Cite BlueZ `3a6b5f5ec`
  (`src/gatt-client.c` `att_exchange` at 5.88 — find its line with `grep -n att_exchange`) and the
  doc section `org.bluez.GattCharacteristic.rst` "uint16 MTU [read-only]" (5.88 :399-403).
- `ATTMTU()`: `mtu` when `mtuKnown`, else 0 (so the channel waits on an unexchanged 23 and settles on
  the signal, the 2 s timeout — then `segmentSizeFor` logs `matter.ble.att_mtu_unknown` and uses the
  minimum, the right size for a true 23 anyway — or the disconnect). `ATTMTUExchanged()` returns the
  channel. `markGone` closes it too (a gone connection settles the wait by `Disconnected` already;
  closing is for symmetry — keep the once).
- Doc: doc.go:23-25 (the MTU property, its 5.62 origin and the exchange signal), README.md:46 row.
- Tests (central_linux_test.go, fake bus fakebus_linux_test.go:172-245: `setProps` sends
  `PropertiesChanged`, `addDevice(p, mtu)`): (a) property 247 at discovery → `ATTMTU()==247`, channel
  closed; (b) property absent → 0 and closed; (c) property 23, then `setProps(c1, ifaceGattChar,
  {"MTU": 185})` → channel closes, `ATTMTU()==185`; (d) 23 and no signal → channel open, `ATTMTU()==0`;
  (e) the full path through `controller/ble.Dial` with the fake clock: (c) sizes the segment from 185
  without a clock advance, (d) sizes at the minimum after `ATTMTUSettleTimeout` on the clock (look at
  how controller/ble's tests drive `segmentSizeFor` with `bletest`, bletest_test.go:245-270).

## Decisions (taken)
- 23 is "not yet known" on BlueZ ≥ 5.62 (waits ≤ 2 s), "known" on < 5.62 only in the sense that nothing
  more will come (no wait). No by_design row: the behaviour is matter.js's wait applied to BlueZ's
  reporting; the BlueZ facts are cited at 5.88 in the Go comments.
- No change in `controller/ble` (issue acceptance).
