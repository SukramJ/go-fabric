## Decisions

1. **bluezoo enters the harness image.** Add `bluezoo==1.0.2` to the Dockerfile's pip step (chip's own pin). Nothing else changes in the image. The new digest is built by the `chip-image` workflow after this wave merges (the assistant dispatches it) and lands by a digest PR; until then every new leg **skips with a named reason** when the image has no `bluezoo` (probe once, as the suite probes its other tools), and never fails.
2. **First, a spike — before any harness code.** In the image with bluezoo pip-installed by hand (a throwaway container, `docker run --privileged`): start chip's bus, `BluetoothMock` and `WpaSupplicantMock` as `linux.py:99-116` does, run `examples/ble-wifi-light` against the app-side adapter and wpa mock, and `chip-tool pairing ble-wifi <node> MatterAP MatterAPPassword <passcode> <discriminator>` (`examples/chip-tool/commands/pairing/Commands.h:174`) with `--ble-controller` naming the other adapter (`test_definition.py:571`). Establish, with the lines of bluezoo's source that decide it: whether bluezoo serves `AcquireWrite`/`AcquireNotify` with fd passing and an `LEAdvertisement1` registered the way `ble/bluez`'s peripheral does it (accept at the first Acquire, `PropertiesChanged` on the advertisement). **If bluezoo cannot carry our peripheral, stop and report** with the evidence — do not bend the peripheral to the mock; the fallback (real `bluetoothd` over `btvirt` in the weekly job only) is the owner's decision.
3. **The leg: `make chiptool-ble-wifi`** — a Go test in `internal/chiptool/` (build tag or env gate as the existing legs) that drives one privileged container: the orchestration in a small Python driver using chip's `matter.testing.linux` classes unchanged (kept under `internal/chiptool/testdata/` or `script/`, cited to `linux.py`), the example binary built for the container's architecture and mounted in, chip-tool `pairing ble-wifi`, then proof over the operational network: a read of `NetworkCommissioning.FeatureMap` (WI), `Networks` (the SSID, `Connected` true), `LastNetworkingStatus` Success, and an OnOff toggle. Assert on the example's log that it left the radio after CommissioningComplete (28a's rule) and that the passphrase `MatterAPPassword` appears in **no** log line of the example. A CI job in `chiptool.yml` beside the existing ones, **not** a required check until the digest PR has run it green; its own control: chip's `all-clusters-app` with `--ble-controller <app adapter> --wifi` under the same mocks, chip-tool with `--ble-controller <tool adapter>` (what chip's suite runs, `scripts/tests/chiptest/test_definition.py:523-525`, `:571`), so a red leg is ours or the environment's by inspection.
4. **Certification cases over the leg.** Classify, case by case, the DD and CNET cases that need BLE or Wi-Fi commissioning (`TC-DD-*` BLE discovery cases, `TC-CNET-4.*` Wi-Fi cases; the list from `internal/chiptool/families_table_test.go` and chip's `src/app/tests/suites/certification/`): run those the mocks can carry (the mock's `BSSs` is empty — a scan-result case cannot pass against it; say so per case), and move each row of `docs/certifiability.md` to its true class with the evidence. No case is acknowledged to make a table green.
5. **btvirt, both directions.** `ble-virtual` gains the second direction: `examples/ble-wifi-light` as the peripheral on real `bluetoothd` over `btvirt` (the first proof of 28a's peripheral against real BlueZ — the `MATTER-<discriminator>` local name, the advertisement, C1/C2), commissioned by matter.js's controller (`script/ble-virtual/controller.mjs`) and by our `pair --ble`. Wi-Fi there: a real `wpa_supplicant` on a `mac80211_hwsim` radio with a `hostapd` AP if the runner's kernel has the module (probe; `modprobe mac80211_hwsim radios=2`), else the example runs with a flag that leaves Wi-Fi out and the job says which variant ran. With hwsim this is also the driver's first run against real wpa_supplicant: a WPA2 passphrase join, a raw 64-hex PSK join, a wrong passphrase (the failed join's network is gone from `ListNetworks` afterwards), an open network.
6. **The manual test plan** `notes/manual-test-plan-m7-ble-wifi.md` (the pattern of `notes/manual-test-plan-0.4.0.md`): Raspberry Pi OS and a generic Linux host — packages, `bluetoothd` and `wpa_supplicant` with D-Bus, NetworkManager off the interface, permissions; `examples/ble-wifi-light` built and started; commissioning with chip-tool, with `reference-controller pair --ble`, and with Apple Home (uncertified-accessory prompt); what to observe per step, the logs to keep, factory reset and a second run; the negative cases (wrong passphrase, AP off, radio blocked). The owner runs it after the tag.
7. **Documents.** `docs/roadmap.md` milestone 7 status and version (v0.22.0), `README.md:35`, `docs/certifiability.md` rows, `docs/guides/` (a short "a node without a network at first boot" guide tying `Network.BLE`, `Network.WiFi.Driver` and the example together), `CHANGELOG.md`. Leave to Fable: `docs/matterjs-comparison.md` (the BLE row and the non-goals), `CLAUDE.md`, `notes/parity/` — list what must change.

## Better than the others, than before, the right cut

- **Than matter.js:** its BLE node is proven on real radios by its users; here the same path is proven in CI on every change to it, against the CSA's own controller. **Than chip:** chip runs its own app under its mocks; this runs a foreign implementation under them, with chip's app as the control.
