## Finding (short; the issue has the long form)

An Apple TV border router answers a Thread node's `_matter._tcp` instance with an SRV whose target is **its own
host** (`Schlafzimmer.local`: fe80, ULA, GUA, IPv4 — all the Apple TV's). Both responders set cache-flush, so the
instance's SRV target flips with the last answer (`client/discovery/name.go:385`, `expireOthersSupersededBy`
`:447-456`; parity with `DnssdName.ts:144-146`, `:216-236`), addresses live per SRV target
(`service.go:454-485` `hostKey`/`updateService`/`deleteService`; `IpService.ts:249-294`), and the connection
accumulates the changes (`client/peer/connection.go:417-430`). Ranking is class → health → DNS priority
(`service.go:76-87`; `ServerAddressSet.ts:165-184`), link-local first (`ServerAddress.ts:170-176`, `:195-209`;
chip `IPAddressSorter.cpp:44-50` likewise). The Apple TV's fe80 therefore leads every reconnect and costs
`DelayBeforeNextAddress` = 45 s (`timing.go:77`; `PeerTimingParameters.ts:195`; the stagger is not shortened by a
failure, `PeerConnection.ts:236-256`, reset only at `:300-303` — ours `connection.go:497-503`, `:603`, `:685`).
A suspect session probes only its current address (`monitor.go:227-247`; `PeerAddressMonitor.ts:105-106`,
`:219-221`, deliberate). chip advances to the next resolved address at once on a CASE timeout
(`OperationalSessionSetup.cpp:457-480`, `TryNextResult`). Neither reference discriminates SRV targets.

## Scope

### §1 D — the SRV target is visible (`client/discovery`)

- `Address` (`service.go:21-30`) gets `Host string`: the SRV target that owns it, lower-cased, no trailing dot
  (set in `updateAddress`, `:522-531`, from `e.name`'s qname; an address two targets name keeps the first owner,
  `addresses.has` already dedups). `CompareDesirability` unchanged here.
- Logs (`status.go:162`, `:172`): `matter.discovery.status.resolving` and `.resolved` carry
  `slog.String("targets", …)` — the current SRV targets, sorted, comma-joined; and a new Info line
  `matter.discovery.srv_target_changed` with `service`, `from`, `to` when a service's set of SRV targets changes
  (`updateService`/`deleteService`), so the flip of #478 is readable without a capture.
- Tests: a two-responder fixture with `deliver` (`helpers_test.go:113`): responder A (node host, ULA) and
  responder B (border-router host: fe80 with source interface, ULA, GUA, IPv4), both cache-flush, alternating;
  assert the `Host` of every address, the target flip after the eviction window, and the log line.

### §2 A″ — the proven host (`client/peer`, `controller/client`)

- `Descriptor` (`client/peer/descriptor.go:15-45`) gets `OperationalHost string`: the discovered SRV target that
  owned the session's address when it was last reached; empty when unknown. `clone` copies it.
- Learn in `followAddressLocked` (`peer.go`, the function that sets `OperationalAddress`): find the
  `p.service.Addresses()` entry whose `AddrPort()` equals the session's address (for TCP, the discovered port as
  today) and set `OperationalHost` to its `Host` when non-empty; `changedLocked()` on change. A session address
  no discovered entry owns leaves the host as it was.
- Rank in `shiftLocked` (`connection.go:514-536`): among the pending targets, those whose `addr.Host` equals
  the peer's `OperationalHost` come first (within them, `CompareDesirability` then the transport index as today),
  then the rest in today's order. The rule applies only while some discovered address carries that host
  (`c.p.service.Addresses()` has one with `Host == OperationalHost`); otherwise today's order. The fallback
  (`maybeAttemptFallbackLocked`, `retireStaleFallback`) is unchanged.
- The monitor's alternates loop (`monitor.go`, the `for _, a := range discovered` of the address-change branch)
  iterates `discovered` — order it the same way (proven host first) through one shared helper, e.g.
  `func orderForPeer(p *Peer, addrs []discovery.Address) []discovery.Address` in `client/peer`.
- Persist: `controller/client/record.go` — new `Record` field `OperationalHost string` with the next free TLV tag
  (see the `rec*` constants `:30-60` and the encoder/decoder `:244`, `:323`); `applyPeer` (`:596-607`) copies
  it from the descriptor, `knownDescriptor` (`:613-625`) back. A record without the tag loads with it empty
  (round-trip test, old-bytes test). `Record.Hostname` (`:72-74`, the *commissionable* SRV host) is a different
  fact and stays.
- Cites in the Go comments: `ServerAddressSet.ts:165-184` (what matter.js ranks by), `PeerDescriptor.ts:48`
  (what it persists), `Peer.ts:142-144`, `:161-163` (where it follows the address), `IPAddressSorter.cpp:44-50`
  and `AddressResolve_DefaultImpl.cpp:130-141` (chip, same ranking, interface kept only for link-local).
- **Register row (Fable text, paste verbatim into the Ahead-of-matter.js table of `notes/parity/by_design.md`;
  the entry it points to is §6):**

### §3 C′ — a failed attempt advances the next address (`client/peer/connection.go`)

- When an attempt ends in a **timeout or network-class** error (what `classifyError` calls transient/network —
  not a peer status error, which means the node was reached) and `c.pending` is non-empty, reset
  `c.lastAttemptAt` and `c.signal()` so the next pending address starts at once; the 45 s stays the stagger
  between attempts that are still running. Site: `handleConnectionError` (`:1004-1090`) after the error is
  classified, before the kick/restart delay logic, which is unchanged. Cite chip `OperationalSessionSetup.cpp:457-480`
  (`OnSessionEstablishmentError` → `TryNextResult` on `CHIP_ERROR_TIMEOUT`/`CHIP_ERROR_BUSY`) and matter.js
  `PeerConnection.ts:236-256` (what is deviated from).
- **by_design entry (Fable text, one paragraph under a new heading
  `### BD-Matter-PeerAttemptFailAdvance — a failed connection attempt starts the next discovered address at once`):**
  matter.js starts the next address of a peer `delayBeforeNextAddress` (45 s, `PeerTimingParameters.ts:195`)
  after the previous attempt *started*, whatever became of it (`PeerConnection.ts:236-256`; `lastAttemptAt` is
  reset only when the fallback is retired, `:300-303`). This module keeps the 45 s as the stagger between
  attempts still in flight but, when an attempt ends in a timeout or network error and addresses are pending,
  starts the next one at once — connectedhomeip's `OperationalSessionSetup::OnSessionEstablishmentError`
  (`src/app/OperationalSessionSetup.cpp:457-480` at 6170af84) moves to the next resolved address on
  `CHIP_ERROR_TIMEOUT`/`CHIP_ERROR_BUSY` without a fixed delay. Reason: a dead first candidate (issue 478: a
  border router's address published for a Thread node) otherwise costs every reconnect 45 s. Retires when
  matter.js advances on failure.

### §4 B — a suspect probe walks the alternates (`client/peer/monitor.go`)

- In `verify`, the alternates loop (today under `if reason == ReasonAddressChange`) also runs for
  `ReasonSessionSuspect` after the current address failed its probe; the address-change-only parts stay as they
  are (the "still discovered → return" early exit, the cooldown and `advanceBackoff`). The migration path
  (`SetAddr`, `followAddress`, `SessionMigrated`, `resetBackoff`) is shared. Update the `ReasonSessionSuspect`
  doc (`:26-29`) and the package doc of the monitor.
- **by_design entry (Fable text, heading
  `### BD-Matter-SuspectProbeWalksAlternates — a session-suspect probe tries the other discovered addresses before the session is given up`):**
  matter.js's `PeerAddressMonitor` walks the discovered alternates only on an mDNS address change; a
  session-suspect run probes the current address and, failing, closes the session
  (`packages/protocol/src/peer/PeerAddressMonitor.ts:105-106`, `:219-221` at db021da0, stated as a decision).
  This module probes the alternates on a suspect session too and migrates the session to one that answers,
  because the full reconnect that follows `handlePeerLoss` costs a Thread node a minute or more (issue 478)
  while a probe costs one small exchange per address. Retires when matter.js walks alternates on suspect.

## Decisions (taken)

- No medium-based exclusion of link-local (the first proposal A): it would have left the router's ULA/GUA/IPv4.
- No shortening of `DelayBeforeNextAddress`, no parallel CASE to one node.
- The proven host is a ranking, not a filter: the other targets stay candidates after it.
