### 3. `ble/bluez` acquired flags

- **chip, read at 6170af84.** `BluezEndpoint.cpp:129`
  (`bluez_gatt_characteristic1_set_write_acquired(aChar, TRUE)`) and
  `:186` (`set_notify_acquired`) set the flags before the call completes.
  chip never sets them false again: the only other uses under
  `src/platform/Linux` are `BluezConnection.cpp:273` (a read) and the
  connection's own `mNotifyAcquired`.
- **Ours.**
  - `setAcquired` (`ble/bluez/peripheral_linux.go`) sets the property and
    sends `PropertiesChanged` on the characteristic before the reply.
  - When a characteristic's socket ends, its flag returns to false, unless
    a newer `AcquireWrite` replaced the socket.
  - `Serve` clears both flags. `objects()` serves the current values.
  - The reset is ours, not chip's. bluezoo keeps the flag per
    characteristic, so a second central would otherwise get
    `acquired == True` with no socket of its own (`characteristic.py:65-77`).
- **Test.** `TestPeripheralAcquiredFlags` checks: both flags set after the
  acquires, a replaced C1 socket keeps WriteAcquired, both flags clear when
  the link goes (with their signals), and the next central acquires afresh.
  30 runs under `-race` passed; the first version was flaky (it read the
  flag before the signal was recorded) and now waits for the signals.
- **Proven end to end.** The leg below runs bluezoo against this
  peripheral with the flags, and the ble-virtual run on `c7761840` runs
  real bluetoothd against it.
