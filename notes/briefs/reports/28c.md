`SendMessage() to BLE failed: src/transport/raw/Tuple.h:267: CHIP Error

no `org.bluez` string and no BlueZ symbol, link libdbus and libavahi only

Dockerfile builds jf-admin/jf-control with the same script. The control leg
(all-clusters-app with `--ble-controller 0 --wifi`) cannot run either. The
existing CNETWIFI/4.23 row already records the same for the Python

**bluezoo carries our peripheral — verified end to end with the module's
own central.** The same container, `ble/bluez/cmd/reference-controller pair
--ble --ble-adapter hci1 --code <QR> --wifi-ssid MatterAP
--wifi-credentials MatterAPPassword`, then `read`: paired; FeatureMap 1,
`Networks` `[{"networkId":"hex:4d61747465724150","connected":true}]`,
LastNetworkingStatus 0; the example logged `matter.ble.central_disconnected`
and `matter.ble.stopped` after CommissioningComplete (left the radio), and
`MatterAPPassword` appears 0 times in its log. The bluezoo lines that
decide it (bluezoo-1.0.2 sdist):

- `bluezoo/gatt/manager.py:46-75` `RegisterApplication` →
  `gatt/application.py:30-36` `GetManagedObjects` on our root, then
  `utils.py:109-126` `GetAll` per object and a `PropertiesChanged`
  subscription; objects without `Handle` get one cached
  (`gatt/manager.py:67-70`).
- `bluezoo/gatt/characteristic.py:61-77` `WriteValue`: with our
  `WriteAcquired` false it calls our `AcquireWrite` with `device`/`mtu`/`link`
  options, `dup`s the fd and writes the value into the socket;
  `:93-131` `StartNotify`: with `NotifyAcquired` false it calls our
  `AcquireNotify`, reads indications from the socket and writes `0x01` per
  indication (the confirmation `ble/bluez` reads, `setNotify`).
- `bluezoo/adv/manager.py:57-75` `RegisterAdvertisement`: `GetAll` on our
  `LEAdvertisement1` and the `PropertiesChanged` subscription (the in-place
  update path); `bluezoo/bluezoo.py:112-125` turns the registered
  advertisement's `LocalName`, `ServiceUUIDs` and `ServiceData` into the
  scanning adapter's device.

One behaviour to note (not a failure): `ble/bluez` keeps `WriteAcquired`
false after an acquire, where chip sets it true
(`BluezEndpoint.cpp:129`, `:186` at `6170af84`). bluezoo decides per write
from the cached property (`characteristic.py:65-77`), so every C1 write is
a fresh `AcquireWrite` and socket, and `setWrite` closes the previous one.
It carried the whole commissioning; real bluetoothd keeps its acquired fd.
Not changed (question 3).

**The defect the spike found (fixed).** First run with our central: PASE,
certificates, `wpasupplicant: connected` — then the reconnect over Wi-Fi
failed ("no address known") for 3 minutes. The example logged
`mdns.responder.udp4_join_failed`/`udp6_join_failed` "no multicast
interface accepted … join" at start and on AddNOC's publish: the
responder's `openSockets` failed when no interface was up, `Publish`
returned the error without registering the service, so nothing was ever
announced, and an interface that came up later was never joined. A node
without a network at first boot — the case milestone 7 exists for — could
not be found on the network it joined. Fix in `mdns/socket.go`:

- `openSockets` (`:68`) keeps a socket that joined no interface (logs
  `mdns.responder.no_interface`), mirroring matter.js
  `NodeJsUdpSocket.ts:189-205` (membership failures logged, socket kept) and
  `UdpMulticastServer.ts:70-83` (only a failed IPv6 socket fails) at
  `db021da0`.
- `joinNew` (`:227`), run on every `links()` listing (each publication and
  each interface check): joins up, multicast interfaces not yet joined,
  logs `mdns.responder.joined`, forgets interfaces that disappeared (a down
  interface stays recorded).
- `bindMcast4`/`bindMcast6` (`:549`, `:603`) return the joined indexes;
  `joinMcast4`/`joinMcast6` keep their contract (error on zero joins) for
  the operational resolver.
- Tests `mdns/socket_live_test.go:329` `TestSockets_JoinNewInterfaces`,
  `:385` `TestOpenSocketsWithoutInterface`; `test` and `-race` green.
- After the fix the spike passed as above (`mdns.responder.joined
  iface=wlx-app-0` 1.3 s before the CASE reconnect).
