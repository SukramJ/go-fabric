## §2 `thread/otbr`

- `otbr.Client` (stdlib `net/http`) after `OtbrRestClient.ts:143-847`: `Node`, `ProbeNode`, `Diagnostics`, `Datasets`, `State`, `NetworkName`, `Rloc`, `Rloc16`, `NumOfRouter`, `ExtAddress`, `ExtPANID`, `BorderAgentID`, `LeaderData`, `ActiveDataset`, `PendingDataset`, `CoprocessorVersion`, `CommissionerState`, `Joiners`, `DiagnosticsCollection`, `Devices`, `DetectDiagnosticsAPI`. JSON numbers are kept as `json.Number` (64-bit counters keep their precision). Errors are `*otbr.Error` with matter.js's codes and the 404/405/409 mapping.
- `otbr.Probe` is `OtbrRestProbe.probe`; `KeyFormat`, `DetectKeyFormat` and `NormalizeKeys` are `OtbrRestCapability.ts` and `caseNormalizer.ts`; `Translate` is `translateNodeJson` for the records the diagnostics server reads.
- The mutations (`setState`, `setDataset`, `deleteActiveDataset`) are unexported. `otbr.BorderRouter` is the one way to them: connectedhomeip's `GenericThreadBorderRouterDelegate.cpp` over REST. The activation PUTs the dataset, enables the interface and polls `/node/state` until the role is attached, bounded by its context (the fail-safe). The revert clears a dataset that an activation set onto a border router without one and no commit confirmed. `factoryReset`, `setCommissionerState`, the joiners and the collection API's actions are not wrapped.
- `thread/otbr/otbrtest`: an httptest border router serving matter.js's recorded fixtures (`test/fixtures/otbr-rest/`, converted to JSON in `fixtures.go`) in both key formats, with an agent's write behaviour (attach after an enable, 409 for a dataset replaced or deleted while up), faults and a "down" switch.

## Differences from the ADR and the brief

- **Values are cached, read at construction, after each command and at `Refresh`**, where chip reads the delegate at every attribute read. A border router is an HTTP round trip away; the cache keeps the data version aware of each change a refresh sees, as 26-B's `ReloadNetworks` does. The host schedules `Refresh` (the daemon every 30 s).
- **A border agent id that is not 16 bytes fails the construction** (and a refresh keeps the last good one) where chip fails the read (`:51-54`): the module's read path has no per-attribute read error.
- **PanChange is the feature selection**, not a port method (`GetPanChangeSupported`, Delegate.h:66): the kit holds the FeatureMap to the selection.
- **The fail-safe check is the node's** (`GeneralCommissioning.FailSafeArmed`), not per accessing fabric (`IsFailSafeArmed(fabricIndex)`, :212), as the Wi-Fi variant does.
- **The activation flag lives in memory:** chip persists `kFailsafeActiveDatasetConfigured` and reverts at `Init` after a reboot (`GenericThreadBorderRouterDelegate.cpp:56-64`); a daemon restarted mid-activation does not revert.
- **ThreadVersion** comes from the border router's own diagnostics record when it carries a Version, else `BorderRouterConfig.ThreadVersion` (the REST surface has no `otThreadGetVersion`); **BorderRouterName** is the host's (`/node` does not carry the MeshCoP service name).
- **NetworkCommissioning's InterfaceEnabled write** accepts the border router's current value and refuses another with FAILURE: chip switches its in-process stack (`SetEnabled`), and the adapter wraps no mutating operation outside the dataset path (ADR decision 4).
- **The Thread NetworkCommissioning server is not mounted by the kit or the daemon.** The device type couples it to ThreadBorderRouterManagement only on an endpoint that also carries SecondaryNetworkInterface (`thread-border-router.ts:34-39`), and the kit composes one device type per endpoint. The server exists, is tested on the wire next to the other two, and is the host's to mount (Question 2).
- **19 attributes, not 17:** the ADR's "17 mandatory attributes (… the provisional ExtAddress and Rloc16)" is 17 mandatory plus the two provisional ones.
- **MACCNT** serves the four counters the REST record carries one to one; the other `[MACCNT]` attributes are optional and unserved.
- **The daemon's endpoint is a bridged device** under the Aggregator (the OTBR is a separate box the bridge exposes), not a root child.
- **`controller/thread` forwards "until the next minor release"**: the ADR's `v0.12.0` window has passed (the module is at `v0.13.5`) (Question 1).
- **No virtual-OTBR run:** the dispatch-only job is added, not run.

## by_design candidates

1. **BD-Thread-TBRM-ChipLogic.** matter.js's `ThreadBorderRouterManagementServer` is the empty subclass (`ThreadBorderRouterManagementServer.ts:14` at `862ad75f`); `cluster/threadbr` serves connectedhomeip's `ThreadBorderRouterManagementCluster.cpp` at `6170af84` over the `BorderRouter` port (`ThreadBorderRouterManagementDelegate.h:63-106` in Go): CASE only (`:151-154`), FAILSAFE_REQUIRED (`:212-215`), INVALID_COMMAND (`:217-221`), INVALID_IN_STATE (`:223-230`), BUSY (`:232-235`), the activation's sequence number and breadcrumb (`:237-243`, `:272-295`), TIMEOUT and the revert at the fail-safe's expiry (`:301-317`), the commit at CommissioningComplete (`:319-322`); `thread/otbr` adapts an OTBR's REST API as `GenericThreadBorderRouterDelegate.cpp` adapts OpenThread, the activation's completion polled from `/node/state`. Reasoning: a controller forms a Thread network through a border router by this cluster, and chip is the only reference with rules. Retire when matter.js's server gains them.
2. **Cached border-router values.** The ThreadBorderRouterManagement and ThreadNetworkDiagnostics servers serve what they read at construction, after each command and at `Refresh`, where chip reads the delegate at every read; a BorderAgentId that is not 16 bytes fails the construction rather than the read. Reasoning: the border router is an HTTP round trip away, and the cache keeps the data version aware of every change.
3. **PanChange is the selection** (chip's `GetPanChangeSupported`), and the activation flag is in memory (chip's persisted `kFailsafeActiveDatasetConfigured`).
