## §1 WiFiNetworkManagement

`cluster/netinfra/wifimgmt.go`: `NewWiFiManagement`, `WiFiManagementServer`.

**Credentials (host state, no port)**
- `SetNetworkCredentials(ssid, passphrase)` follows `:74-103`. It refuses an SSID outside 1 to 32 bytes and a passphrase that is not WPA personal (`:44-56`) with `ErrInvalidCredentials`. The same pair reports nothing.
- `ClearNetworkCredentials` follows `:62-72`.
- `HasNetworkCredentials`, `SSID` and `Passphrase` are the getters.

**The surrogate.** A new passphrase sets `PassphraseSurrogate` to the last value plus one, or to the real time in milliseconds when that is later (`:94-99`, on the server's `clock.Clock`). An SSID change alone leaves the surrogate.

**NetworkPassphraseRequest** (`:129-138`)
- A request that is not CASE is UNSUPPORTED_ACCESS. No credentials is INVALID_IN_STATE.
- The session-kind seam is `isCASE(ctx)`. The bridge stamps the fabric and subject (`bridge/receive_dispatch.go:511-515`) and marks PASE (`im.IsPASEFromContext`) and group messages (`bridge/group_messaging.go:339-350`, `im.GroupSubjectFromContext`). CASE is a fabric plus a node subject that is neither, the rule `cluster/core/ota_provider.go:346` uses.

**The passphrase**
- It is never logged (the server does not log).
- It is never in an error: the validation error names the length only, and a test asserts this.
- It is never an attribute.
- The typed `Set` cannot move `Ssid` or `PassphraseSurrogate` (`spec.ErrNotHeld`).

**Tests:** `wifimgmt_chip_test.go` ports all 10 cases (`:58-243`). A group context is added to the CASE case. The surrogate case adds the real-time rule.

## §2 ThreadNetworkDirectory

`cluster/netinfra/threaddir.go`: `NewThreadDirectory`, `ThreadDirectoryServer`, `MemoryThreadNetworkStore`.

**The port** `ThreadNetworkStore` (= `threadnetworkdirectorydef.ThreadNetworkStore`, generated through the `ports` map in `script/clustergen/declare.go`, `Declare.ThreadNetworkStore`):
- `Capacity`, `LoadNetworks`, `SaveNetwork` and `RemoveNetwork`. This is chip's storage interface without the iterator and without `GetNetworkDataset`: the server serves the datasets from its own table.
- The server checks the capacity and the presence of a network itself, so the store has no sentinels. A store error is FAILURE.
- The in-memory default holds 32 networks, chip's `CHIP_CONFIG_MAX_THREAD_NETWORK_DIRECTORY_STORAGE_CAPACITY` = 2 × `CHIP_CONFIG_MAX_FABRICS` (`CHIPConfig.h:1891`, `:799`).

**Dataset checks** (`:231-245`)
- The framing follows chip's `OperationalDatasetView::IsValid` (`ThreadOperationalDataset.cpp:151-164`).
- The first sub-TLV of each type is read, as `Locate` reads it (`:172-185`).
- Then chip's getter sizes (`:193-301`) apply: the ten sub-TLVs, the three-byte Channel on page 0, a PSKc of 16 bytes, a name of at most 16 bytes, and a non-empty Channel Mask.
- The brief named `controller/thread.DecodeDataset` (`controller/thread/dataset.go:53`). The first build used it, and `script/archcheck` refused it: `cluster/netinfra -> controller/thread (servers -> roles)`. The checks are now the package's own, after chip's view. Once wave 26a moves the codec to `thread/`, it can be used again.

**Status codes**
- AddNetwork: CONSTRAINT_ERROR, INVALID_IN_STATE for an Active Timestamp that is not newer, RESOURCE_EXHAUSTED.
- RemoveNetwork: CONSTRAINT_ERROR for a size other than 8 or for the preferred network, NOT_FOUND.
- GetOperationalDataset: UNSUPPORTED_ACCESS without CASE, CONSTRAINT_ERROR, NOT_FOUND.
- A `PreferredExtendedPanID` write follows `:139-151`: an empty value is null, and an ID must name a stored network.

## Differences from the brief

- **Release number.** The brief's title says `v0.13.5` and concept v10 §C says `v0.13.7`. No release is cut here; the entry is under `[Unreleased]`.
- **§3 needed no change.** The test lives in `device/`: the rule is the kit's (Initial supplies a value), as matter.js's case is node-level.
- **ThreadNetworks comes from the server's table.** chip reads the storage on every read (`:153-183`). This server loads the store at construction and after each command. A host that writes the store outside the cluster calls `ReloadNetworks`. The ported list case uses it in place of chip's "add directly to storage".
- **The preferred network is server state, not part of the port.** chip keeps it in attribute storage (`:113`, `:150`). The host persists it from the change reports and hands it back as `Initial.PreferredExtendedPanId`, which must name a stored network, or construction fails.
- **The dataset is not decoded through `controller/thread`** (the archcheck layering, see §2). It is checked as chip's view reads it.
- **An empty Network Name is refused** (CONSTRAINT_ERROR). chip accepts it, but the struct's constraint "1 to 16" could not serve it.
- **Decode order on the wire.** The generated decoder refuses an Extended PAN ID that is not 8 bytes before the server runs. A non-CASE GetOperationalDataset with a wrong-sized ID therefore answers CONSTRAINT_ERROR where chip answers UNSUPPORTED_ACCESS. The status for a CASE request is the same.
- **A group message is not CASE**, as chip's `kGroup` auth mode is not.
- **Beyond the brief:** the wire test and the device declaration test.

## Decisions

- **The WiFi credentials** go through typed setters on the mounted server. A host reaches them with `d.WiFiNetworkManagement().Underlying().(*netinfra.WiFiManagementServer)`, as for the thermostat's inbound setters. There is no port.
- **The store port has four methods.** Capacity and presence are checked by the server. `SaveNetwork` returning `ErrStoreFull` is also mapped to RESOURCE_EXHAUSTED.
- **The store calls run under the server's lock.** The store must not call back into the server.
- **Credentials stay in memory**, as chip keeps them (`WiFiNetworkManagementCluster.h:67-69`). The host sets them at every start.

## Left out

- The migration case `:514`.
- A persisted preferred network inside the port.
- A typed device accessor for the netinfra servers.

## Questions

1. **Reaching the setters.** Hosts reach `SetNetworkCredentials` and `ReloadNetworks` by asserting the type of `Underlying()`. Should the device facade instead get typed accessors for the kit's own servers (here, and for `thermo`)?
2. **The preferred network.** Keep `PreferredExtendedPanID` as server state persisted by the host from the change reports? Or add `LoadPreferred`/`SavePreferred` to `ThreadNetworkStore`, as chip keeps it in attribute storage?
3. **ThreadNetworks.** Keep the table with `ReloadNetworks`? Or read the store on every read, as chip does (which costs a store call per read and leaves the data version unaware of out-of-band changes, as chip's is)?
4. **The empty Network Name.** Accept the refusal (CONSTRAINT_ERROR) as a `by_design` divergence from chip?
5. **The dataset codec.** Should wave 26a, once the codec lives in `thread/`, switch `cluster/netinfra`'s dataset check to it? Or should the check keep chip's view (first sub-TLV, chip's sizes), which the codec does not mirror? The codec reads the last occurrence and accepts the one-byte Channel.
6. **The register rows.** Are the two row names and markers right, and which `by_design` texts should they get?

## by_design candidates

1. **BD-chip-WiFiNetworkManagement-RulesInServer.**
   - matter.js `WiFiNetworkManagementServer.ts:14` at `862ad75f` is the generated stub.
   - `cluster/netinfra` serves chip's `WiFiNetworkManagementCluster.cpp` at `6170af84`: the credentials as host state through `SetNetworkCredentials` and `ClearNetworkCredentials` (`:62-103`), the SSID and WPA-personal checks (`:44-56`, `:76-77`), the PassphraseSurrogate rule (`:94-99`), and NetworkPassphraseRequest over CASE only (`:129-138`).
   - Reasoning: a Network Infrastructure Manager must hand its passphrase to a commissioner, and matter.js leaves that to the application.
2. **BD-chip-ThreadNetworkDirectory-RulesInServer.**
   - matter.js `ThreadNetworkDirectoryServer.ts:14` at `862ad75f` is the generated stub.
   - `cluster/netinfra` serves chip's `ThreadNetworkDirectoryCluster.cpp` at `6170af84`: AddNetwork `:213-276`, RemoveNetwork `:278-307`, GetOperationalDataset `:309-335` and the preferred-network write `:139-151`. The datasets sit behind the `ThreadNetworkStore` port, after `ThreadNetworkDirectoryStorage.h`.
   - Reasoning: the directory's checks are what keeps a stale dataset from replacing a live one.
3. **The empty Network Name is refused.** chip's `ThreadOperationalDataset.cpp:257-265` checks the maximum only; the module's ThreadNetworkStruct is "1 to 16". This applies only if Question 4 is answered yes.
4. **ThreadNetworks is served from a table with `ReloadNetworks`**, where chip reads the storage on every read (`:153-183`). This applies only if Question 3 keeps the table.
