## §2 The persisted digest

`node/surface_stability.go`. Per endpoint the node stores, in the settings
table next to the ConfigurationVersion, `{"digest": <hex>, "surface":
<canonical surface.Surface JSON of the endpoint, number left out>}`:

- a bridged endpoint and a part under `bridged_surface_digest.<key>` (the
  family of `bridged_configuration_version.<key>`, key = `SourceKey.String()`);
- the Aggregator, and a host topology's endpoint without a stable key,
  under `bridged_surface_digest.@<number>` (the `bindingKey` convention);
- the root under `basic_information.surface_digest` (as
  `rootConfigVersionKey`).

Nothing is in `endpoint.Record` or the endpoint store: no store migration,
no host store interface change. The surface itself is stored beside the
digest so a restart can name the change as a `surface.Diff`
(difference 1). The stored digest is recomputed from the stored surface
when that decodes, so a change of the canonical encoding (S2 changed it
once) is no surface change.

## §3 The announcement

`Node.announceSurface` runs after `bridge.Start` in `Node.Start` and after
every `Aggregator` reassembly (`Add`, `Replace`, `Remove`, `Batch`, under
the reassembly lock). Per endpoint of the bridge's topology: no stored
surface → store it, nothing raised; same digest → nothing written;
different → one `IncreaseNodeConfigurationVersionWith` change for all
drifted endpoints, raising each drifted bridged endpoint through the new
`ConfigurationChange.IncreaseEndpointConfigurationVersion(id)` (a part
raises the bridged endpoint it belongs to; root, Aggregator and the OTA
provider part raise nothing of their own) and the root once; then the
versions are persisted (`storeConfigVersions`), the endpoint's Descriptor
and every cluster the diff names get `BumpClusterDataVersion`, the new
surface is stored, a `surface.SurfaceChange` is recorded (last 100) and one
`slog` Info `surface changed` is logged with `key`, `endpoint`, `from`,
`to` (12 hex digits) and `changed` (the diff, one string per change).

Withheld (S3 carry-over): `recordWithheld` drops the stored surface of a
withheld key (writes `""`, only when one is stored), so its return is a
first assembly.

## Differences from the brief

1. **The surface is stored with its digest**, not the digest alone: the
   brief asks for `Report.Changed[].Changes` (a `Diff`) across a restart,
   which needs the earlier surface. One settings value per endpoint.
2. **Per-endpoint raise.** The existing `ConfigurationChange.IncreaseConfigurationVersion(scope, address)`
   raises every endpoint of a physical device (30 in the bridge's own
   test), and an empty `DeviceAddress` would match every device without
   one. New additive API `IncreaseEndpointConfigurationVersion(id)` inside
   the same `IncreaseNodeConfigurationVersionWith` change.
3. **Parts** carry no BDBI; a part's change raises its bridged endpoint's
   version (walk up `ParentEndpointID`), a part under the root (the OTA
   provider) the root's alone.
4. **DataVersions of the root and the Aggregator are not bumped:** their
   servers are persistent instances without a bump API (Descriptor derives
   its version from its lists, `cluster/core/descriptor.go:66-77`); a root
   change only happens across a restart, where every tracker starts at a
   fresh random value (`contract/dataversion.go:51`).
5. **Log keys** `from`, `to`, `changed` (the slogkeys table has no
   `before`/`changes`); message `surface changed` as briefed.
6. **ADR 0030 decision 6** says "persisted with its endpoint record"; the
   brief overrides that (settings, not `endpoint.Record`). The ADR text is
   not changed.
7. `surface.SurfaceChange` stutters; kept as briefed with a `nolint:revive`.
8. The announcement runs after `bridge.Start` returns, so the listener is
   already open for the few milliseconds it takes.

## Decisions taken

- A stored value that does not decode counts as none (first assembly,
  warning logged).
- `Batch` carries its `Partition.Batch` context so dropping a withheld
  endpoint's surface runs under the caller's context (contextcheck).
- `storeConfigVersions` takes a context.
- An unkeyed host-topology endpoint is reported as `@<number>`.

## Left out

A renumbering mode (E.1), profiles (S5), any store migration, any edit of
`notes/parity/`. No dirty mark for the changed clusters' attributes beyond
ConfigurationVersion (the brief asks for DataVersions). No announcement
when a host calls `bridge.Reassemble` itself (only the node's own paths).
No chip-tool fixture run (no new served cluster).

## Observed, not fixed

its inner clusters, no Descriptor (`endpoint/materialize.go:231-236`). The

## Questions

1. Is the per-endpoint raise (difference 2) the intended semantics, or
   should a change raise every endpoint of the physical device as
   `Aggregator.IncreaseConfigurationVersion(key)` does?
2. Should the changed clusters' global attributes also be marked dirty for
   subscribers, beyond the ConfigurationVersion report?
3. Should ADR 0030 decision 6's "with its endpoint record" be amended to
   "in the node's settings next to the ConfigurationVersion"?
