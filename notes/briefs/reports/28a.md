## Differences from the brief and why

1. **`BLEConnection` gains `OnUnsubscribe(func())`.** The brief's port has
   no way to report the end of the C2 subscription, on which matter.js
   closes (`BlenoBleServer.ts:81-84`); on BlueZ it is the end of the notify
   socket. Platform-forced; the only signature change to the port.
2. **`btp.Accept` takes `btp.GATTConnection`, not `contract.BLEConnection`.**
   `script/archcheck` places `transport/...` below `contract`
   (model-and-protocol), so `transport/btp` cannot import it;
   `GATTConnection` is the identical method set, and the bridge hands its
   `contract.BLEConnection` straight in. `Accept` returns at once and hands
   the `*btp.Conn` to an `open` callback, because the session exists only
   after the subscription.
3. **`node.Config.Network.BLE`, not `node.Config.BLE`.** matter.js keeps
   `ble` in the node's network state (`NetworkServer.ts:28-34`), and
   `node.Network` already holds `TCP` and `WiFi`. Still one field.
4. **`bridge/commissioning_window.go:978` keeps on-network only.** That
   `CommissioningWindowOpener` opens an administrator's enhanced window
   (`OpenWindow`), which BLE never announces (`BleAdvertiser.ts:40-42`),
   and it has no access to the bridge's config. The node's payloads
   (`node/credentials.go`) carry the bit as decided.
5. **A connection that is not TCP is no longer closed with its last
   session** (`bridge/conn.go:416`), not named in the brief: otherwise a
   PASE session's close (fail-safe expiry) dropped the BLE link, where
   matter.js closes only a TCP channel (`ExchangeManager.ts:770-775`).
6. **The stale TCP sentence of `bridge/bridge.go`'s package doc was stale**
   (verified: `receive` serves unsecured messages on a connection) and is
   rewritten with the BLE paragraph.
7. **The window's close takes the node fully off the radio** (as the brief
   decides). matter.js only ends the advertisement there
   (`BleAdvertisement.ts:69-71`) and keeps the BLE transport until the node
   is commissioned (`ServerNetworkRuntime.ts:294-308`); the difference shows
   only for an uncommissioned node whose window timed out (48 h).
8. **connectedhomeip reports no unsubscription on the AcquireNotify path**
   (`HandleTXCharCCCDWrite`, `BLEManagerImpl.cpp:699-712`, is only reached
   with `NotifyAcquired` true at the pin); `ble/bluez` takes the notify
   socket's end as it, which is BlueZ's documented behaviour
   (`src/gatt-database.c` `ccc_write_cb`, BlueZ master — not a pin).
9. **`fabrictest.Device.BLE()` needs `Topology.BLE`** and returns the
   device's one peripheral on every call (before: a new peripheral per call,
   no opt-in), because the node must be built with the radio.
10. **`bridgetest.ServeConn` keeps its API** but the seam changed:
    `bridgeseam.ServeConn` replaces `ReceiveOnConn`/`ConnClosed` (internal).

## Decisions taken

- `StartBLE` takes the `CommissioningAdvertisement` the node already builds
  for mDNS (discriminator, vendor, product, CM) — one shape for both
  announcements; `StopBLE` takes a `ctx` because it waits for the platform.
- A second central is refused (disconnected), not queued: matter.js's
  peripheral serves one connection; a queued central would wait out its own
  15 s handshake timer anyway.
- The node bounds `StopBLE` in a window transition by 5 s on its clock
  (`bleStopTimeout`), as the mDNS withdraw is bounded.
- `Accept` hands the connection to `open` under its lock once the session's
  handshake response is confirmed, so no message can precede `open`; the
  session's disconnect callback closes on its own goroutine (the session
  calls it while the subscription holds the lock — unsupported version).
- `ble/bluez` accepts a central at its first `AcquireWrite`/`AcquireNotify`
  (its first use of the Matter service), not at `Connected=true` as chip
  does: a phone connected to the host for something else is not a Matter
  central and must not take the bridge's one slot.
- `ble/bluez` holds a subscription that bluetoothd reports before the first
  C1 write was read until that write is delivered: C1 arrives over a socket,
  the subscription over D-Bus, and matter.js refuses a subscription before
  the handshake (`BlenoBleServer.ts:288-291`); a central always writes the
  request before it subscribes (`controller/ble/channel.go` `handshake`).
- C3 is always exported (matter.js serves it); chip exports it only with
  `CHIP_ENABLE_ADDITIONAL_DATA_ADVERTISING`.
- `bletest.Radio.Peripheral()` was not added (the peripheral is the
  receiver of `Radio()`; one way in).
- `fabrictest`: BLE is opt-in per device (`Topology.BLE`), so the QR codes
  and the clock of every other site test do not move.

## Questions

1. Should the window's close keep the GATT service registered until the
   node is commissioned, as matter.js keeps its BLE transport, instead of
   unregistering it with the advertisement (difference 7)? Recommendation:
   keep the brief's cut — one radio state per window state, and an
   uncommissioned node whose window timed out reopens nothing either way.
2. Should the endpoint topology learn `Network.BLE`, so a BLE node drops
   `CustomNetworkConfig` as matter.js does (`ServerEndpointFacts.ts:131-145`)?
   It needs an `endpoint` field; no verdict changes today, since every root
   mounts NetworkCommissioning. Recommendation: with 28b, when the Wi-Fi
   variant becomes a public node knob.
3. `ble/bluez` accepts a central at its first `AcquireWrite`/`AcquireNotify`,
   not at `Connected=true` as chip (`BluezEndpoint.cpp:325-357`): a host's
   other BLE clients must not take the bridge's single slot. Confirm.
4. The `LocalName` `MATTER-<discriminator>` (chip) goes into the scan
   response under legacy advertising (BlueZ `advertising.c`
   `generate_scan_rsp`); matter.js advertises no name. Keep chip's name?
   28c's proof over real BlueZ/bluezoo should confirm both the name and the
   in-place `PropertiesChanged` update of `ServiceData`/intervals.
5. `make lint`'s 5-minute golangci-lint timeout was exceeded twice on this
   machine under the guard bundle's load (0 issues with 30 m) — raise it in
   the Makefile?

## `by_design` candidates

- **`BD-Matter-BLEPeripheralOverBlueZ`** — matter.js's peripheral is bleno
  on the HCI user channel (`packages/nodejs-ble/src/BlenoBleServer.ts:26-31`,
  `:352-387` at db021da0: raw EIR, no name); `ble/bluez` follows chip's
  D-Bus plumbing (`src/platform/Linux/bluez/BluezEndpoint.cpp:448-534`,
  `BluezAdvertisement.cpp:43-189`, `BLEManagerImpl.cpp:377` at 6170af84):
  the advertisement composed by BlueZ from `ServiceUUIDs` `fff6`,
  `ServiceData`, `Discoverable`, `LocalName` `MATTER-<discriminator>` (in the
  scan response), `MinInterval` = `MaxInterval`; the adapter stays
  bluetoothd's. C3 always exported (matter.js), unlike chip's compile flag.
- **`BD-Matter-BLEWindowCloseLeavesRadio`** (if question 1 keeps the cut) —
  `ServerNetworkRuntime.ts:294-308` keeps the BLE transport until
  commissioned; the node unregisters the GATT service with the window.
- **`BD-Matter-BLEOneCentralRefused`** — matter.js serves one connection
  because bleno does (`BlenoBleServer.ts:129-133`); the bridge refuses
  (disconnects) a second central on any platform.
- **`BD-Matter-BLEC1RefusalLogged`** — matter.js answers a refused C1 write
  with `RESULT_UNLIKELY_ERROR` (`BlenoBleServer.ts:51-57`); the port's
  `OnWrite` has no result (BlueZ delivers C1 over a socket and has answered
  already), so `btp.Accept` logs the refusal.
- **`BD-Matter-BLESubscriptionHeldForFirstWrite`** (`ble/bluez`) — a C2
  subscription reported before the first C1 write was read is held until
  it was; matter.js refuses such a subscription (`BlenoBleServer.ts:288-291`),
  which on BlueZ is an arrival order, not the central's.
- **`BD-Matter-BLEUnsubscribeFromNotifySocket`** (`ble/bluez`) — chip does
  not report it (`BLEManagerImpl.cpp:699-712`); the notify socket's end is
  the unsubscription matter.js closes on (`BlenoBleServer.ts:81-84`).
- Findings register, not by_design: `CustomNetworkConfig` for a BLE node
  (question 2; `ServerEndpointFacts.ts:131-145`).
