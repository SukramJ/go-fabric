## §2 Chime (chip, ahead of matter.js)

`cluster/camera/chime.go`. Port `ChimePort{InstalledChimeSounds() ([]ChimeSoundStruct, error); PlayChimeSound(ctx, id) error}`.

- InstalledChimeSounds read from the port on every read (a spec.Source);
  an error, or a list the schema refuses, fails the read (`:119-121`,
  `:137-173`); `SoundsChanged` reports a change.
- SelectedChime write: NOT_FOUND for an id not installed, checked before
  the no-op (`:215-226`); Enabled (`:228-238`); an unchanged value is no
  report. Defaults 0 / true (`ChimeCluster.h:95-96`).
- PlayChimeSound (`:258-303`): disabled → success, nothing plays; a given
  unknown ChimeID → NOT_FOUND; the port's status, FAILURE without one;
  success emits ChimeStartedPlaying.
- **Persistence:** no store record for such attributes → the host
  persists through the change notification and restores through
  `Initial` / `ChimeConfig` (findings note added).
- **Tests:** `chime_chip_test.go` ports the 12 `TEST_F` (:99-300);
  `TestChimePlayRules` covers :271-303, which no chip case reaches.

- Brief §2: "NOT_FOUND when the selected chime is no longer installed

  SelectedChime is not checked at play. Ported as chip has it.
- Brief §3: 17 `TEST_F` — 13 are cluster cases (ported), 4 test chip's
  storage migration (`TestMigrate…`, :885-1035), not ported.
- chip lists MPTZPresets under MPAN (`Logic.cpp:117`); the served list
  follows the definition (MPRESETS). Identical for the test fixture.
- chip starts the next preset id at 1 after a restart; here it moves past
  a restored preset (`skipTakenPresetID`), since chip would append a
  second preset 1 (:1062, :1105-1110).
- Persistence is the host's (no store record); the findings register
  says so.
- The over-the-wire requestor test needs TCP (large messages), so it runs
  on loopback sockets.

## Decisions

- Port names: `RequestorPort` (brief), `ChimePort`, `MechanicalPTZ` /
  `MechanicalPresets` / `DigitalPTZ` (per feature, as ContentControl's
  optional interfaces).
- The requestor's port methods return nothing (matter.js observables);
  the command's answer does not depend on the host.
- The ACL entry goes through the node, as the OTA provider's does, and
  emits no event (matter.js); the OTA provider's existing install still
  calls `NotifyAdminEntryInstalled` (event) — see Questions.
- Group invokes and local calls of the four commands answer FAILURE.

## Left out

- chip's storage-migration cases (4).
- Clearing a removed fabric's sessions: not done, as in matter.js (owner, Q3).
- A requestor added by a later reassembly gets its ACL entry at the next
  Start or commissioning, not at once.

## by_design candidates

1. **BD-chip-Chime-RulesInServer.** matter.js `ChimeServer.ts:14` at `862ad75f` is the generated behaviour; `cluster/camera.Chime` follows connectedhomeip `ChimeCluster.cpp` at `6170af84` (`:176`, `:215-238`, `:258-303`) behind the `ChimePort`. A chime without its rules would accept any SelectedChime and never play.
2. **BD-chip-CameraAvSettings-RulesInServer.** matter.js `CameraAvSettingsUserLevelManagementServer.ts:18` is the generated behaviour; `cluster/camera.AvSettings` follows chip `CameraAvSettingsUserLevelManagementLogic.cpp` (`:721-1284`) behind `MechanicalPTZ` / `MechanicalPresets` / `DigitalPTZ`; MPTZPresets is served under MPRESETS (the definition), not MPAN (`:117`). The generated behaviour validates no target against the limits.
3. **BD-chip-CameraAvSettings-NextPresetAfterRestore.** chip starts `mCurrentPresetID` at 1 whatever is stored and would append a duplicate preset 1 (`:1062`, `:1105-1110`); here the next id skips a restored preset. A duplicate id breaks MoveToPreset and RemovePreset.
4. **BD-Matter-WebRtcRequestor-ACLThroughNode.** matter.js installs the Operate entry inside the behaviour (`WebRtcTransportRequestorServer.ts:56-94`); here the node does it at Start and after CommissioningComplete (`node/webrtc_requestor_acl.go`), as for the OTA provider, because a cluster server has no access to the node's ACL. Both installs are local changes and emit no AccessControlEntryChanged (`AccessControlServer.ts:284-302`). The requestor keeps a removed fabric's sessions until the host removes them, as matter.js does (its server has no fabric-removal hook at the pin).
