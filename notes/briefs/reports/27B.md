## §1 Reported session parameters — `node`, `bridge`

Commit `09101ab2`.

- `node.Config.Sessions *node.SessionIntervals{Idle, Active, ActiveThreshold}`; nil and zero fields are matter.js's `SessionIntervals.defaults` (500 / 300 / 4000 ms, `SessionIntervals.ts:36-50`).
- Validation: a threshold above 65535 ms is refused, as `SessionManager.ts:58-67` refuses it. matter.js leaves SII/SAI unbounded; here a negative value, a sub-millisecond value and an interval above uint32 ms are refused too, because the wire carries whole milliseconds.
- The intervals reach the PASE and CASE responders (`responderSessionParams`) and the operational DNS-SD record (`bridge.Config.SessionIntervals`, new), as `ServerNetworkRuntime.ts:357-363` and `DeviceAdvertiser.ts:361-364` do. The record caps them (mdns `capAdvertisedIntervals`, `SessionIntervals.forAdvertisement`).
- An ICD's record keeps the ICD's threshold and, while LIT, no SII (`IcdManagementServer.ts:482-495`). The session parameters are not changed by ICD, as in matter.js.
- `Node.SessionParameters()` returns what the node reports.
- Tests: `node/session_intervals_internal_test.go` (the issue-89 pattern: CASE and PASE responders; validation, 7 cases), `node/session_intervals_test.go` (New refuses 70 s; the accessor), `bridge/advertised_intervals_test.go` (defaults, configured, capped, ICD).
- **Left out:** matter.js `ReportedSessionParametersTest.ts` (2 cases) stays `planned`. Both read the device's record of what the controller sent, and `secure/operational.Entry` stores the peer's intervals without a getter (a `secure/` change). The register reason and the findings row now say so.

## §2 The device-side BDX MRP delay — `bdx`, `bridge`, `node`

Commit `1c9b773c`.

- `node.Limits.BDXAdditionalMrpDelay` (not negative, `SoftwareUpdateManager.ts:60-67`) becomes the BDX responder's default margin (`bdx.Responder.SetAdditionalMrpDelay`).
- `bdx.ScopeConfig.AdditionalMrpDelay` overrides it per scope (`BdxProtocol.ts:223`).
- The responder sets it on the accepted exchange before the messenger takes it (`BdxProtocol.ts:139-142`), through `bdx.MrpDelayExchange`.
- The bridge's responder exchange implements it. Its sends track with `outboundReliableTracker.TrackWithMargin`: the margin joins the base interval and the backoff amplifies it (`MRP.ts` retransmissionIntervalOf `additionalDelay`; `MessageExchange.ts:1219-1222`).
- Tests:

## Differences from the brief and the read map

- **§4, one endpoint vs parts.** The brief asked for one endpoint with two device types. matter.js counts a simple component only below the composite, and concept v10 0.5 names PartsList composites. The constructors compose parts, and the kit's one-device-type-per-endpoint rule does not change (Question 1).
- **§3, three events chip does not emit as the brief assumed.**
  - chip never calls `GenerateOccupancyChangeEvent`; the event is in the EventList with OCC and never emitted.
  - chip at `6170af84` has no schedule server, so `ActiveScheduleChange` keeps the earlier pin's emit (`645b267a`).
  - The SetpointChange call sites for the user limits reach a switch without a case, so a limit emits nothing.
- **§3, ActivePresetChange on an unchanged handle.** chip emits it on every accepted `SetActivePresetRequest`, the same handle included, and on every write of a setpoint in effect. Here the second one emits only when a preset was active: the clear runs matter.js's `#assert…SetpointChanging`, which returns when none is.
- **§3, ThermostatRunningMode without AUTO.** chip's test serves ThermostatRunningMode without AUTO as an optional attribute. The model's conformance is "TEVT & AUTO, [AUTO]", so it is served only with AUTO and the port uses AUTO.
- **§5, TimeZone list lengths.** A SetTimeZone list over two entries is refused by the request's own constraint ("1 to 2") before the handler: CONSTRAINT_ERROR on the wire, where chip answers RESOURCE_EXHAUSTED (:1168-1171). The handler's check answers RESOURCE_EXHAUSTED for a host-side caller. An empty list is refused the same way on the wire; the handler would restore the default entry.
- **§5, IPv4 as NTP server.** An IPv4 address is a "domain" by chip's default delegate (it has a dot and is not IPv6). With `SupportsDNSResolve` it is accepted, as in chip.
- **§5, no DSTTableEmpty at startup.** chip emits DSTTableEmpty when the stored DST list is missing at startup (`ClearDSTOffset` in `Startup`). The Go server's emitter is attached after construction, so no event goes out then.
- **§6:** the check already held (see §6). chip answers InvalidValue for a value outside the enum; the kit's definition answers ConstraintError, as for any value outside a type (matter.js's validation).
- **§1:** the read map's `ServerNetworkRuntime.ts:354-362` is `:357-363`.
- **§2:** matter.js's device-side BDX margin is the network profile's BDX class (`NetworkProfile.ts:156-159`) or a scope's `additionalMrpDelay`. `LimitsConfig.bdxAdditionalMrpDelay` feeds the former; the node maps it to the responder's default, and the scope's overrides it.

## Decisions

- `bridge.Config.SessionIntervals` (the record) is the bridge's; the node owns the validation.
- `bdx.MrpDelayExchange` is an optional interface on `bdx.Exchange`; an exchange without it keeps its own margin.
- `thermo.ThermostatServer.SetEndpoint` follows the `boolcfg`/`pump` pattern for host-change events.
- TimeSynchronization persists under `timesync.*` settings keys as JSON (the TLS and Datastore pattern).
- The node adapter needs `Config.Client`; without it nothing is mounted and the announcement answers FAILURE as before.

- chip TimeSynchronization: the two TimeSource-optional blocks; the trusted-time-source client (reading UTC from the source); SetUTCTime's clock setting and TimeNotAccepted.

## Questions

1. **Composite shape.** The brief named one endpoint with two device types; matter.js counts a simple component only on an endpoint below the composite, and concept v10 0.5 says PartsList composites. The constructors compose the components as parts and the one-type-per-endpoint rule stays. Keep the parts composition, or also allow a superset device type (OnOffLight under FloodlightCamera) on the composite's own endpoint?
2. **Reported session parameters of the peer.** `ReportedSessionParametersTest.ts` needs the device's record of what the controller sent, which `secure/operational.Entry` keeps without a getter. Add `Entry.PeerMRPIntervals` (a `secure/` change, Fable) and `SessionInfo` fields in a follow-up, or leave the file planned?
3. **SetUTCTime.** The server still accepts SetUTCTime without effect. chip validates the granularity and the time source (InvalidCommand) and answers TimeNotAccepted for a coarser granularity than the current one (:1110-1136). Port those statuses while keeping the clock the node's, or leave SetUTCTime as it is?

## by_design candidates

1. **BD-chip-Thermostat-Schedules, events paragraph (addition).** The Events feature follows connectedhomeip as well: matter.js's `ThermostatServer.ts` emits none of the eight events (its only emit is `calibratedTemperature$Changed`, :525 at `862ad75f`). `cluster/thermo/events.go` emits them where `ThermostatClusterEvents.cpp` and its call sites at `6170af84` do: SystemModeChange (`ThermostatClusterBase.cpp:158-162`), LocalTemperatureChange (:179-183), RunningModeChange (:246-250), RunningStateChange (:283-287), SetpointChange for the four setpoints (`ThermostatClusterSetpointsBase.cpp:63-85`) and ActivePresetChange (`ThermostatClusterPresets.cpp:461-500`). ActiveScheduleChange keeps the `645b267a` emit; OccupancyChange is never emitted, as in chip. ThermostatRunningMode is served with TEVT and AUTO (`SetThermostatRunningMode`, chip's `SetRunningMode` checks). Without them a controller that subscribes to the events hears nothing.
2. **BD-Matter-TimeSync-NoUTCFeature, replacement of the last sentence.** "… UTCTime and Granularity are mandatory regardless of any feature flag. The optional TZ, NTPC, NTPS and TSC features are served after connectedhomeip when the host selects them (`core.TimeSynchronizationConfig`, `node.Config.TimeSynchronization`; `BD-chip-TimeSynchronization-Features`), and `FeatureMap` is the selection, 0 by default."
3. **BD-chip-TimeSynchronization-Features (new, Ahead-of-matter.js register row).** Marker: `TimeSynchronizationServer.ts:14`, `export class TimeSynchronizationServer extends TimeSynchronizationBehavior {}` (absence). `cluster/core/time_synchronization_features.go` follows `TimeSynchronizationCluster.cpp` at `6170af84`: the gating (:186-248), the four handlers (:1138-1275), the list rules (:619-816), LocalTime and the state updates (:874-1007), the fabric removal (:1020-1028), persisted through `store.Settings`. 4. **BD-chip-TimeSync-ListConstraintBeforeHandler.** A SetTimeZone list over two entries is CONSTRAINT_ERROR from the request's constraint (matter.js validation) before chip's RESOURCE_EXHAUSTED check (:1168-1171) can answer. matter.js's field validation decides where it models the constraint.
5. **BD-chip-AirQuality-NoDefault.** chip starts AirQuality at Unknown (`AirQualityCluster.h:43`); the kit's server starts unset, as matter.js gives an enum without a default no value (`DefaultValue.ts:26-75`). A host sets the first value.
