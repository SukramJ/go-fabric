## Differences from the brief

- **SensorFusion is not in the matter.js model** (`ambient-context-sensing.element.ts:22-29`: HA, OC, OI, AUD, PRED; the attributes end at PredictedActivity 0x000B). The "five feature bits" are four plus PRED; `SetSensorFusionSupported` (`:480-496`) and `CheckSensorFusionSupported` (`:915-927` — the brief's `:915-925` is this one, not the setter) are not ported.
- **No port, so no `ports_sensing.go`:** every delegate method became server state, the clock or a `Set`; the clustergen edits are the `hosts` entry and the `clusters.go` comment.
- **No sensors guide exists;** the page covering the measurement servers is `getting-started/device.md`'s Devices section, too general for the section, so the guide is a new page `guides/sensing.md`.
- **No precedent for a kit server on a type that does not list its cluster:** the kit refuses a kit `Declare` for an unlisted cluster (`… has no server cluster requirement`); only `HostServer` mounts there. The factory is registered for types that list the cluster (none at the pin).
- **The model's constraints at rest:** AmbientContextType ("1 to simultaneousDetectionLimit") and ObjectCount ("min 1", default 0) refuse their values at rest (an empty list, 0), which chip serves; both are answered from the server's state (a `spec.Source`), not stored.
- **SimultaneousDetectionLimit:** the model's "1 to 10" adds the minimum 1 to chip's `<= 10` (`:389`).
- **ObjectCountConfig persistence:** chip persists the threshold only (`:357-364`, `:65-72`); the host gets and restores the whole struct.
- **EventStartTimeSys** is milliseconds since the server was built (the boot epoch `cluster/core` DiagnosticLogs uses); chip's is the monotonic clock since boot.
- **Host errors:** chip's `CHIP_ERROR_INVALID_ARGUMENT` is `spec.ErrInvalidValue`, `CHIP_ERROR_INCORRECT_STATE` `sensing.ErrNotSupported`; a ConstraintError rule on the host path is `spec.ErrInvalidValue` wrapping the CONSTRAINT_ERROR status.
- `kWriteSuccessNoOp` (`:393`, `:425`) is a plain success.

## Decisions

- `AddDetection` and `SetObjectCount` are Host methods (inputs with a timer and an event; ObjectCount may be unserved); the configuration attributes go through `Set` — CK-2's rule that what `Set` reaches stays out of `Host`.
- `HoldTime` nil starts at `HoldTimeLimits.HoldTimeDefault` (chip's `WithHoldTime` sets both together; its defaults agree).
- A persisted `ObjectCountConfig` is checked against the model and the label rule only; chip's supported-list rule cannot apply before the list is set.

## Questions

1. **A kit server for an unlisted cluster.** No device type lists AmbientContextSensing as a server; the kit refuses `acsdef.Declare{Features: …}` on any type, so a host builds `sensing.NewAmbientContext` and mounts it as `HostServer`. Keep that (recommendation: yes, no facade change while no type lists the cluster), or let a kit `Declare` mount the kit's server on a type that does not list the cluster, as matter.js's `MutableEndpoint.with` adds any behavior?
2. **A repeated detection.** chip adds the hold to the detection's first start (`:284`, `item->mStartTimestamp + newHoldTime`), so the same detection again reorders the list but never extends its hold, and near HoldTimeMax shortens it. Mirrored. Keep chip's (recommendation), or hold from the repeat (the intent the comment at `:241` states)?
