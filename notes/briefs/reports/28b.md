## Differences from the brief

- The `WiFi` condition: the root now states the RootNode condition WiFi for
  a `WiFi` with a Driver only as well (before: with a Reporter only). The
  validator derives WiFi from the NetworkCommissioning feature anyway, and
  the conformance under it is optional, so nothing new is required.
- The scan timeout's status: chip's driver has no scan timeout (the
  cluster's bounds it); a scan that does not end in time, or ends by the
  context or `Close`, is UnknownError here.
- Non-UTF-8 credentials are refused like a non-UTF-8 SSID (the brief named
  only the SSID).
- BSS properties are read with one `GetAll` per BSS, not one `Get` per
  property: the GDBus proxy chip creates loads them the same way.
- The example's test exercises `newNode` with in-process radios, not the
  `main` binary (the brief allowed either; 28c drives the binary).

## Decisions taken

- The driver logic is in untagged files (only the system bus and `New`
  are Linux-only), so its tests would run on any platform.
- `Options.Logger` nil is `slog.Default()` (as `node.Config.Logger`).
- A D-Bus error's text is logged for calls that carry no credential;
  debug texts carry only D-Bus error names.
- `reannouncingDriver` passes the call's context to `TriggerReannounce`
  (the responder ignores it).

## Left out

- `SaveConfig`, DHCP, PDC, AP mode, Wi-Fi PAF (decision 3, on purpose).
- No removal of the added network after a failed or timed-out join:
  chip leaves it too; the next join removes the current network only, so
  failed attempts can accumulate in wpa_supplicant's in-memory list (see
  questions).
- No run against a real wpa_supplicant or chip's mock here (28c).

## Questions

1. A 64-hex-digit raw PSK as Matter credential: chip and this driver send it
   as the string `psk`; whether wpa_supplicant's D-Bus handler takes a
   64-character string as a raw PSK or as a (too long) passphrase was not
   verified against wpa_supplicant (its documentation does not say). 28c's
   mock does not judge it.
2. Should a failed or timed-out join remove the network it added (chip
   does not)?
3. Should the WiFi condition follow the Driver too (done), or stay tied to
   the Reporter as before?

## `by_design` candidates (text for Fable)

- No `SaveConfig` (chip WPA `:1118-1135` via `CommitConfiguration`,
  `NetworkCommissioningWiFiDriver.cpp:135-167`): the node's store holds the
  committed network and `Start` rejoins it; the credential lives in one
  place.
- No DHCP client (`PostNetworkConnect`, `CHIP_DEVICE_CONFIG_LINUX_DHCPC_CMD`,
  WPA `:1098-1115`): addressing is the host's.
- Open networks: `key_mgmt "NONE"` without `psk` where chip sends `psk ""`
  with `"SAE WPA-PSK"` (`:936-940`).
- A non-UTF-8 / NUL SSID is refused (UnknownError) instead of being
  truncated or mis-encoded by a C string.
- The scan's own timeout (UnknownError) where chip leaves it to the cluster.
- The re-announcement after a successful join (decision 2) — matter.js's
  example, not its `NetworkCommissioningServer` (`NetworkCommissioningServer.ts:18`
  is an empty class); an *Ahead of matter.js* row may fit better, since
  matter.js ships no Wi-Fi driver at all.

- **R1:** `ConnectNetwork` marks the join busy (`connecting`) but installs the
  attempt only through `listen` (`driver.go:418`), after `Disconnect`
  returned and right before `SelectNetwork`. The run loop (`driver.go:205`)
  first handles the signals already queued without an attempt and only then
  installs it. godbus puts a signal into the channel inside its read loop
  before it reads the next message (`conn.go` `handleSignal`,
  `default_handler.go:316-325` at v5.2.4), so the signals sent before the
  Disconnect reply are queued by the time `Disconnect` returns. A
  `disconnected` before any `associating` is still ignored. The limit is a
  burst of more than 256 queued signals: godbus then delivers late from a
  goroutine, and such a signal can reach the attempt. Not handled (the
  coordinator ruled this out). Test `TestConnectIgnoresStatesBeforeSelect`
  (`driver_test.go:515`) covers a stale `associating` plus Disconnect's
  `disconnected` followed by Success, and a stale `associating, completed`
  pair where the old code returned a false Success and the join now times
  out. It fails on the previous driver.
- **R2:** `removeAdded` (`driver.go:442`) calls `RemoveNetwork(network)` on

  `Close` now waits for in-flight calls (`calls` WaitGroup) before it
