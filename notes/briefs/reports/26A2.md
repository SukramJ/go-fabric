## Differences from the brief

- chip's test file has 64 `TEST_F`: 57 cluster cases (ported) and 7 of `TestCodegenCameraAVStreamManagementMigration` (`:1790-1929`, chip's storage migration; left out, the host persists).
- The brief's feature list (SPDN, NGHT, LACT, SHLD) is not the definition's: at the pin the features are ADO, VDO, SNP, PRIV, SPKR, ICTL, WMARK, OSD, STOR, HDR, NV; the gates follow those.
- ZoneManagement: the Sensitivity write is `:259-284` (`:262` the range check); the command dispatch is `:327-363`, `:402-443` are `AddOrUpdateTrigger` / `RemoveTrigger`. `Delegate.h:37-150` holds.
- chip's `AcceptedCommandsFollowFeatureGates` and `GeneratedCommandsEmptyWhenCreateIsNotSupported` build USERDEFINED without TWODCART; the definition makes USERDEFINED `[TWODCART]`, so the selection is refused (`ErrZonesConfig`); the port asserts the refusal and checks TWODCART alone.
- chip gates the reads of MaxConcurrentEncoders and MaxEncodedPixelRate on VDO (`:575-590`) but lists them for VDO or SNP (`:2007-2008`); the definition's VDO | SNP is served.
- chip's image bound `kMaxSnapshotImageSize` (`h:53-55`) follows the platform's large packet buffer; here `DefaultMaxSnapshotSize` is matter.js's MaxTCPMessageSize fallback less chip's 100 bytes (63900), configurable (`AvStreamConfig.MaxSnapshotSize`).
- `IsValidAnalysisZone` (`Delegate.h`) is a query for PushAvStreamTransport; it is not in the port — `Zones.ZoneList` answers it for 26-A3.
- chip calls the delegate under its single thread; here the port is called outside the server's lock, and the id it returns is matched afterwards (a concurrent second allocation of the same id is a reuse).

## Decisions

- Port names `VideoStreamPort`, `AudioStreamPort`, `SnapshotStreamPort`, `SnapshotCapturePort`, `ZonePort`; the snapshot request reaches the port as a `SnapshotStreamStruct` (id and count ignored), not a new args type.
- chip's `OnStreamUsagePrioritiesChanged` / `OnAttributeChanged` are the server's change notification.
- chip's member defaults for attributes the definition gives no default; the definition's default where it has one.

## Left out

- chip's storage-migration cases (7) and `TestZoneManagementClusterBackwardsCompatibility.cpp`.
- A store record for the streams, zones and settings (owner decision Q5 of 26-A1: host-side).

## Questions

1. **Defaults without a model default.** CameraAvStreamManagement starts the attributes the matter.js model gives no default at chip's values (NightVision On, the max levels 254, StatusLightBrightness Medium, the rest 0/false), and keeps the model's where it has one (MicrophoneAGCEnabled and StatusLightEnabled `true`, chip `false`). Keep this, or take chip's values throughout, or require the host to set every mandatory one (matter.js refuses a missing mandatory attribute)?
2. **The snapshot bound.** Default 63900 bytes (matter.js's 64000 MaxTCPMessageSize less chip's 100), configurable. Keep, or bind it to the session's negotiated MaxTCPMessageSize at invoke time?
3. **MaxZones.** chip checks only the user-defined budget, not MaxZones over all zones (`:473`); mirrored. Keep chip's, or also refuse beyond MaxZones?

## by_design candidates

1. **BD-chip-CameraAvStreamManagement-RulesInServer.** matter.js `CameraAvStreamManagementServer.ts:18` at `862ad75f` is the generated behaviour; `cluster/camera.AvStream` follows connectedhomeip `CameraAVStreamManagementCluster.cpp` at `6170af84` (Init `:76-160`, the handlers `:2065-2669`, the reference counts `:486-557`, `SetViewport` `:1137-1171`) behind a port per encoder and the capture. The generated behaviour validates no allocation against the capabilities and keeps no stream table.
2. **BD-chip-ZoneManagement-RulesInServer.** matter.js `ZoneManagementServer.ts:14` is the generated behaviour; `cluster/camera.Zones` follows chip `ZoneManagementCluster.cpp` (`:85-106`, `:259-284`, `:445-733`) and `zone-geometry.h:158-317` behind the `ZonePort`. Without the rules a controller could store a self-intersecting or duplicate zone.
3. **BD-chip-CameraAvStream-DefaultsWhereTheModelHasNone.** The attributes the matter.js model gives no default start at chip's member values (`CameraAVStreamManagementCluster.h:405-445`, `:740-764`); the model's default stands where it names one (MicrophoneAGCEnabled, StatusLightEnabled). A served attribute without a value would fail every read.
4. **BD-chip-CameraAvStream-SnapshotBound.** chip's `kMaxSnapshotImageSize` (`h:53-55`) derives from the platform's large packet buffer; here the bound is matter.js's MaxTCPMessageSize fallback (`secure/sessionparams`) less chip's 100 bytes, configurable. The module has no packet buffer to derive it from.
5. **BD-chip-ZoneManagement-UserDefinedNeedsTwoDCart.** chip's tests build USERDEFINED without TWODCART (`TestZoneManagementCluster.cpp:223-239`, `:308-315`); the matter.js model makes USERDEFINED `[TWODCART]`, and the definition refuses the selection. Schema values come from matter.js verbatim.
