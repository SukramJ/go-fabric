## 2 #228 — a native-ramp device by declaration

- **Ports into `levelcontroldef`.** `NativeRamp`, `NativeMover`,
  `NativeSwitcher` are generated through `script/clustergen/declare.go`'s
  port table (the `LevelSource` entry at :93 is the pattern), with the
  doc text of `cluster/levelcontrol/native.go:20-76` carried over.
  `NativeMover` and `NativeSwitcher` are documented as optional
  interfaces of a `NativeRamp`, found by type assertion. `time.Duration`
  in the method strings needs the generator to emit the `time` import.
  Add one optional interface, `NativePersister`
  (`PersistLevel(ctx context.Context, options OptionsBitmap, onLevel *uint8) error`),
  which carries `NativeConfig.Persist` (`native.go:89-92`) for the kit
  route. No caller in this repository sets `Persist`; the owner keeps it
  (2026-10-23) because loom's two profiles persist Options and OnLevel
  through it today, and without it the declaration route loses that. Remove the three from `cluster/levelcontrol`. `NewNativeSource`
  stays there for the seam route and takes `levelcontroldef.NativeRamp`.
  `cluster/light/colorcontrol_transitions.go` names NativeRamp only in
  comments (:356, :366); update the comments' qualifier.
- **Declaration.** `levelcontroldef.Declare` gains `Ramp NativeRamp`.
  If both `Ramp` and `LevelSource` are set, `device.New…`/`FromSpec`
  refuses with `fmt.Errorf("%w: levelcontrol: Ramp and LevelSource are exclusive", ErrConfiguration)`
  (`device/device.go:27`, the pattern of `device/options.go:157`). In
  `device/defaults_ports.go` `newLevelControlPortServer` (:94), a set
  `Ramp` builds `levelcontrol.NewNativeSource(d.Ramp, onOff, NativeConfig{…})`:
  - `onOff`: the sibling OnOff server through `onOffOf`, as the
    `Transitions` path does at :102-104. Without a sibling, pass nil:
    `NewNativeSource` treats nil as "no coupling" and lets every command
    pass the ExecuteIfOff gate (`native.go:393`, `:425`).
  - `Lighting`: from the feature selection.
  - `Options`: `consume8(b.initial, lvldef.AttrOptions)`.
  - `OnLevel`: `consume8(b.initial, lvldef.AttrOnLevel)`, then `&v`
    when present and nil when absent. A null OnLevel never appears in
    the map, because the typed Initial writes the key only for a non-nil
    `OnLevel` (`cluster/spec/levelcontrol/server_gen.go:139-140`).
  - `Persist`: from `NativePersister` if the ramp implements it.
  - `Clock`: `b.clock`.

  The host therefore needs no `levelcontrol.OnOff`; say so in the
  field's doc.
- **Tests.** On `fabrictest`: a dimmer and a volume (non-Lighting)
  declared with `Ramp`. MoveToLevelWithOnOff switches the sibling OnOff.
  A `NativeMover` takes Move. A `NativeSwitcher` takes the "with On/Off"
  pair. `NativePersister` sees a write of Options. Both fields set →
  the error.
- CHANGELOG `### Added` (`Declare.Ramp`) and `### Removed` (the three
  interfaces at their old path, with the new one), guide rows.

## 3 #232 — a Stop the closure server would ignore

`closurecontroldef` gains an optional interface of the declared
`Mover`, generated beside it (`script/clustergen` port table, the
`Mover` entry at `declare.go:171`):
`StopObserver { StopIgnored(ctx context.Context) error }`.

`cluster/closure` `invokeStop` (`closurecontrol_server.go:358-367`):
in the default branch (the state is not Moving/WaitingForMotion/
Calibrating), if the mover implements `StopObserver`, call
`StopIgnored`. An error answers FAILURE, as a `Mover.Stop` error does.
Otherwise nothing changes: no state write, no report, SUCCESS. The
moving case is untouched.

matter.js has no Stop logic in
`packages/node/src/behaviors/closure-control/ClosureControlServer.ts`
at the pin: a case-insensitive grep for `stop` finds nothing (checked
2026-10-23). Say so in the comment. The no-op rule
is cluster §5.4.8.1 as the server's comment states. The interface is a
bridged host's affordance, like `NativeSwitcher`: `by_design`
candidate.

Tests: idle Stop with an observer → called, SUCCESS, MainState and
reports unchanged. Observer error → FAILURE. Moving Stop → `Mover.Stop`
only, observer not called. No observer → as today. CHANGELOG
`### Added`.

## 4 #229 — completeness per partition

- **API (`node/aggregator.go`).** `func (a *Aggregator) Partition(name string) *Partition`
  returns the same handle for the same name; `""` or `Scope` is the
  default partition. `*Partition` has `Add`, `Replace`, `Remove`,
  `MarkComplete`, `Batch` (§5) and `Endpoints`, with the Aggregator's
  semantics. The Aggregator's own methods are the default partition's,
  so a host without partitions sees no change.
- **Keys.** A StableKey is unique across all partitions, because the
  endpoint store is keyed by `source_key`: `ErrDuplicateKey` across
  partitions, and `Replace`/`Remove` with a key of another partition →
  `ErrUnknownKey`. `IncreaseConfigurationVersion(s)` find a key in any
  partition.
- **Snapshot.** `snapshot()` (:358) emits one `endpoint.Snapshot` per
  partition that exists: the default first, then others in creation
  order. Each partition has its own `Scope` = name and its own
  `ModelComplete`. An empty partition still emits its snapshot, so a
  complete partition whose devices were all removed collects them. The
  OTA provider stays in the default snapshot.
- **Retiring a partition.** A source that leaves the host's
  configuration (a CCU removed) gets no handle after a restart, so no
  snapshot ever lists its scope, and its stored numbers would stay
  forever. Add `func (a *Aggregator) RetirePartition(ctx context.Context, name string) error`:
  - It refuses the default partition with `ErrRetireDefault`.
  - It refuses a partition that holds endpoints with
    `ErrPartitionNotEmpty`.
  - It needs no handle. On the next assembly it adds one snapshot
    `{Scope: name, ModelComplete: true}` with no endpoints, so the
    assembler's GC (`endpoint/assembler.go:370-405`) collects every
    record of that scope. After that the name is forgotten.
  - On a running node it reassembles at once; before `Start` the
    retirement rides on Start's assembly.

  Tests: a store holding records under scope "ccu2", no handle →
  `RetirePartition("ccu2")` collects them. The default partition →
  error. A partition with an endpoint → error.
- **Store fact the issue gets half right.** `assignOrReuseID`
  (`endpoint/assembler.go:325-337`) rewrites `rec.Scope` only when the
  device type drifted. A record reused under another scope keeps its old
  one, so the new partition's GC never lists it. Make the reuse path
  upsert when `rec.Scope != scope` too, with a test (moved from
  partition A to B, B complete, removed from B → collected). This is how
  loom's per-CCU scopes and a host's move from the default partition
  stay collectable.
- **Tests.** Two partitions with one marked complete: only its vanished
  stored numbers go, and the other's survive. A partition never marked
  complete keeps everything. A cross-partition duplicate key fails. A
  default-only host behaves exactly as at `v0.10.1` (the existing
  Aggregator tests unchanged).
- `by_design` candidate: matter.js has one endpoint tree and no
  partitions; the partition extends the existing
  `BD-Matter-EndpointGC-ModelCompleteGate`. CHANGELOG `### Added`.
  Docs: `docs/guides/host-view.md:215-221` describes `Add` and
  `MarkComplete`. Add a paragraph there on partitions, `RetirePartition`
  and `Batch`. `docs/getting-started/device.md:142` stays as it is.

## 5 #231 — one reassembly for many changes

`func (a *Aggregator) Batch(ctx context.Context, fn func(b *Batch) error) error`
and `(*Partition).Batch`. `*Batch` has `Add(ep)`, `Replace(key, ep)`,
`Remove(key)`, `MarkComplete()`, bound to the partition the batch was
opened on.

- Each call validates and changes the set at once, under `a.mu` as
  today, and returns its own error. It does not reassemble.
- `fn` runs without any Aggregator lock held, so `fn` may call other
  methods.
- After `fn`, if the node is started and at least one change applied:
  exactly one `reassemble`. Then the devices that were removed or
  replaced are unbound, as `Remove` and `Replace` do after their
  reassembly.
- The result is `errors.Join(fnErr, reassembleErr)`. What applied
  before an error stays applied (owner decision: one faulty device must
  not block a fleet).
- Before `Start`, a batch only changes the set.
- Document that a concurrent Add/Remove from another goroutine
  reassembles on its own and may show part of a running batch.
- Factor `Add`/`Replace`/`Remove` onto the batch-internal operations, so
  each is a one-change batch and has no second implementation.

Tests:
- Count reassemblies. No existing test counts them. Add an
  `atomic.Int64` field to `Aggregator`, incremented in `reassemble`
  (:345) after a successful `Reassemble`, and expose it only through
  `node/export_test.go`.
- 300 adds give one reassembly.
- A failing add in the middle: the others applied, one reassembly, the
  error returned.
- Remove inside a batch unbinds after the reassembly.
- `MarkComplete` inside a batch: GC in the same assembly.
- `make race` covers a batch concurrent with an Add.

CHANGELOG `### Added`.
