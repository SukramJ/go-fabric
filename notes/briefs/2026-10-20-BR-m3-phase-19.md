## What is settled before you build

- **The client stack on fabrictest comes first.** `node/client.go:62-107`
  opens a kernel socket (`udp.New`) and its own DNS-SD cache
  (`discovery.Open`), so two nodes on a site cannot reach each other over
  CASE. First commit of this wave: the node's client stack takes the
  site's socket and names — the smallest seam in `node.Config.Client`
  (the `udp` seam fabrictest already uses for the server socket,
  `fabrictest/net.go`, and a `*discovery.Names` the site answers,
  `fabrictest/mdns.go`); `fabrictest.Device` exposes the node's `Peers()`;
  a `fabrictest` test has device A invoke a command on device B of the
  same fabric. No change to `contract/`; a change to `node.Config` is
  named in the report. BQ estimated ~40 lines seam, ~50 lines wiring.
- **OTA on a site with two devices.** matter.js hosts the provider on the
  controller; Go hosts it on a node (`node.Config.OTAProvider`,
  `node/ota_provider.go`). The port commissions two devices on the site's
  controller: the provider device (`OTAProvider` with an `OTAImageSource`
  holding the test image, an `OTAConsent`, an `OTAApplyPolicy`,
  `OnStatusChange`) and the requestor device (`Config.OTA` with an
  `OtaApplier` that records what `applyUpdate` got); the requestor's
  `DefaultOTAProviders` names the provider device; BDX runs over the
  site's network. The requestor cases (OtaTest.ts:91-706, :1049, the Busy
  `describe` :581-705) assert on the requestor's `UpdateState`
  transitions, events and the provider's hook calls, as the map lists.
- **The `SoftwareUpdateManager` cases.** Where a case's observable is a
  wire answer of the provider (QueryImage / ApplyUpdateRequest response,
  `delayedActionTime`, the token rules :1437-1577, the apply delay
  :1639-1653, queryImage cases A/B/C :2288-2524) or a hook call, it is
  ported on the Go provider. Where it drives the manager's own bookkeeping
  (`queuedUpdates`, `addUpdateConsent`/`hasConsent`, `bdxTransferOptionsFor`
  :1157-1216, the stalled detection by BDX progress :1660, :1980-2239,
  `RebootResubscribeArmer` and `closeForPeer`/`handlePeerShutdown`
  :706-1049, `suppressNextStartUp` :2593-2684, the DCL store cleanup
  :2772), it is `missing` with the reason "controller-side
  SoftwareUpdateManager: <what>" unless the Go provider already carries
  the state (`updateInProgress`, `inProgressAnswer`, the RebootDetected
  path of `ota_provider_test.go`). No new manager in Go in this wave: the
  report's **The SoftwareUpdateManager** section lists each case with its
  Go hook or its reason, and the whole is one Register candidate.
- **The small servers.** A case with no runtime assertion (EnergyEvseMode
  :54, :69; FanControl :8; OccupancySensing :19; RvcOperationalState :63)
  is ported as the construction it performs, or `missing` "js-runtime-only:
  a TypeScript type assertion" when it has no runtime at all. The
  measurement range rules (:44, :53), the occupancy event (:33), the
  TimeFormatLocalization constraint (:37) and the CommodityTariff null
  members (:50) are fix candidates where the Go server answers
  differently.
- **The open partial cases (decision 19.4).** Every `missing` title ends
  this wave with one of: a `by_design` id in the reason (the owner writes
  the entry from the report's candidates), "js-runtime-only: <what>" (a

  extension of a behavior class), or "M4: <findings entry>" (a node
  option or clock form the module has not: the wall-clock-only step of
  `clocktest.Fake` for DoorLock :1366 and GeneralDiagnostics :27, the
  extension access check :355). The rest is ported or fixed: the fix
  candidates are BooleanState :12, HepaFilterMonitoring :47/:84,
  ConcentrationMeasurement :43/:65, GroupKeyManagement :147,
  ConfigurationVersion :110, the five AtomicWriteHandler commit cases
  :393-491 (over the wire on a commissioned pair, as the others of that
  file), OperationalCredentials :346/:352 (the fabric event for

## How a port is built

BO §"How a port is built" items 1–9, with these deltas:

- Files: `node/ota_parity_matterjs_test.go` (the two-device OTA cases) and
  `cluster/core/ota_provider_parity_matterjs_test.go` (the provider's
  answers; the three existing functions there stay); one
  `<server>_parity_matterjs_test.go` per small-server file in its Go
  package; the open partial cases in the existing parity files of their
  entries; `node/sessions_parity_matterjs_test.go`,
  `node/events_parity_matterjs_test.go`; `controller/client/
  <file>_parity_matterjs_test.go` for the four controller files; the
  binding default-subscription cases in
  `node/binding_integration_parity_matterjs_test.go`.
- Commit messages `m3/phase-19 BR: <File>Test.ts <describe> → <package>
  (<n> cases, <m> missing)`; a fix `m3/phase-19 BR fix: <one sentence>
  (<matter.js file>:<lines>)`; the stack `m3/phase-19 BR: fabrictest node
  client stack`.
- Guards as BO item 8 (`make race` mandatory). The families to run locally
  after a fix that moved device behaviour: `GOFABRIC_CHIP_FAMILIES=SU,ACL,IDM
  make chiptool-families` (SU is the OTA family against the reference
  daemon; IDM/10.4 whenever a PICS moved; `-update-chip-cases` only when
  the diff is read and explained in the report).
- Branch `m3/phase-19`, one pull request labelled `needs-chiptool`, no
  auto-merge; the owner enables it after the review.
