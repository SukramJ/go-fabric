## Decisions

1. **The port is `contract`'s.** `contract/ble.go` (stdlib only), beside `contract.WiFiDriver`: the two radios a device-side host supplies are both host ports.
   - `BLEPeripheral`: `Advertise(ctx, BLEAdvertisement) error` (starts, or replaces the running one), `StopAdvertising(ctx) error`, `Serve(ctx, c3 []byte, accept func(BLEConnection)) error` (registers the Matter GATT service, calls `accept` once per central, unregisters and drops the connection before it returns when ctx ends).
   - `BLEAdvertisement{Data []byte; Interval time.Duration}` — `Data` is the complete advertising payload matter.js hands its peripheral (`BlePeripheralInterface.advertise`, `packages/protocol/src/ble/Ble.ts:31-34`).
   - `BLEConnection`: `Remote() string`, `OnWrite(func(value []byte))` (C1 writes, in order), `OnSubscribe(func(attMTU int))` (the C2 subscription, with the connection's ATT_MTU), `Indicate(ctx, value []byte) error` (returns once the central confirmed), `Disconnect() error`, `Disconnected() <-chan struct{}`. Names follow `controller/ble.Connection` where the roles meet.
   - Adjust a signature only where the platform forces it; report every change.
2. **The BTP peripheral server is platform-independent and in `transport/btp`**: `Accept` (name yours) turns a `contract.BLEConnection` into a `*btp.Conn` after `BlenoBleServer.ts`: the handshake request is kept from the C1 write (`:251-270`), the 15 s `BTP_CONN_RSP_TIMEOUT` runs until the C2 subscribe (`:148-149`, `:258`, `BleConsts.ts:56`), the session is created at the subscribe with `min(ATT_MTU-3, maxValueSize)` (`:288-300`), a subscribe before a handshake and a second session are refused (`:289-296`), an indication's confirmation completes the write (`:304-310`, `:329-`), a C2 unsubscribe closes (`:83`), a disconnect closes the session (`:195-210`). Timers through the package's clock seam; no `time.Sleep`/`time.After`.
3. **The bridge serves BLE as it serves TCP: `bridge.Config.BLE contract.BLEPeripheral`** and two methods, `StartBLE(ctx, …)` / `StopBLE()` (names yours), driven by whoever drives the mDNS announce. `StartBLE` registers the GATT service, accepts one central at a time, feeds each BTP connection into `receive` in delivery order (the ordering of `bridgetest.ConnServer` becomes the bridge's own unexported code; `bridgetest.ServeConn` keeps its API on top of it), and advertises on matter.js's schedule: the same payload at `earlyInterval` 20 ms for 30 s, `lateInterval` 150 ms until 15 min, `extendedInterval` 1285 ms after (`BleAdvertisement.ts:13-71`, defaults `BleAdvertiser.ts:102-105`), payload from `BtpCodec.encodeBleAdvertisementData` as `:74-85` calls it (the extended-announcement flag after 15 min). `StopBLE` stops advertising, disconnects and unregisters. MRP stays off over BTP by `Reliable()` (`Session.ts:368-370`); a lost connection evicts its sessions (`evictConn`; `BleChannelClosedError`, `Ble.ts:17-22`). No other new exported bridge API.
4. **BLE follows the uncommissioned node only** (`ServerNetworkRuntime.ts:255-275`: a commissioned node advertises on IP only; `:294-308`, `:385-389`: on `commissioned` the BLE advertiser and transport are deleted). In `node`: `Config.BLE contract.BLEPeripheral`; the commissioning host starts BLE where it announces the node's own or basic window while the node has no fabric, and stops it on CommissioningComplete, on the window's close, and at `Stop`. A commissioned node never touches the radio, also not for a window an administrator opens. After the last fabric is removed BLE returns with the node's own window (`reopenIfDecommissioned`).
5. **The onboarding payload names BLE when BLE is configured** (`NetworkServer.ts:36-51`: `discoveryCaps.ble` follows the BLE support, `onIpNetwork` defaults to true): `setup.DiscoveryOnIP|setup.DiscoveryBLE` at `bridge/commissioning_window.go:978` and `node/credentials.go:102`.
6. **C3 is served empty**: matter.js serves it, the additional data only when `commissioning.ble.aad` is set, and nothing sets it (`BleAdvertisement.ts:35`, `:82`). No `aad` knob in this wave; the advertisement's additional-data flag stays 0.
7. **`ble/bluez` implements the port over D-Bus after connectedhomeip** (matter.js's peripheral is bleno on raw HCI — nothing to mirror for BlueZ): a GATT application under an ObjectManager root with service `fff6`, C1 `write`, C2 `indicate`, C3 `read` (`src/platform/Linux/bluez/BluezEndpoint.cpp:451-502`), C1 through `AcquireWrite` and C2 through `AcquireNotify` with the `mtu` of the options (`:97-217`), `GattManager1.RegisterApplication`; the advertisement as `LEAdvertisement1` — `Type` peripheral, `ServiceUUIDs`, `ServiceData`, `Discoverable`, `LocalName`, `MinInterval`/`MaxInterval` (`BluezAdvertisement.cpp:43-189`) — through `LEAdvertisingManager1.RegisterAdvertisement`. Read `BluezConnection.cpp` and the indication-confirmation path yourself and cite what you mirror. The `bus` seam grows what exporting objects and passing file descriptors needs; the fake bus plays bluetoothd for the peripheral (registers the application, connects a central, acquires, writes, reads indications). New public constructor `bluez.NewPeripheral` with the central's adapter option. No cgo. `LocalName`: chip's `MATTER-<discriminator>`; say where matter.js sets none.
8. **`fabrictest.Device.BLE()` moves onto the production path**: an in-process `contract.BLEPeripheral` (in `controller/ble/bletest`, or a new `bridge/bridgetest` helper — one, not two) joins `bletest`'s central to a node built with `Config.BLE`, so the commissioner's BLE tests run through `bridge.Config.BLE`, not through `ServeConn`. `bletest.Peripheral` stays for the fault and stall models the central's tests need.

## Better than the others, than before, the right cut

- **Than matter.js:** its peripheral needs bleno's native build and the HCI user channel, which takes the adapter away from bluetoothd; ours is pure Go over BlueZ's D-Bus API and shares the adapter. The BTP peripheral server is separated from the platform (matter.js's `BlenoBleServer` mixes both, its own TODO at `Ble.ts:24`), so every platform and the test fake share one tested implementation. **Than chip:** the same BlueZ plumbing without GLib and cgo.
- **Than before:** a device without a network at first boot can be commissioned; the tests' BLE route becomes the production route instead of a seam beside it.
- **The cut:** radios are host ports in `contract` (Wi-Fi and BLE alike), BTP and the lifecycle are the module's, BlueZ is a nested module a host without BLE never pulls. The node facade gains one field.
