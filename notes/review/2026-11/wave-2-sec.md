## W2-sec-01 — high — Interaction Model requests are accepted over the unsecured session (SessionID==0) and evaluated as the fabric-0 commissioning bypass

**Where:** `bridge/receive.go:260-269` (`dispatch` → `handleIMOpcode` with no secure-session requirement), `bridge/im_gate.go:38-52` (`classifyIMOpcode` rejects only non-request opcodes and group-session Read/Subscribe/Timed — never an unsecured session), `bridge/receive_dispatch.go:200-205,504-520` (`resolveSessionFabric(0)=0`, `resolveSessionPASE(0)=false`), `endpoint/dispatcher.go:1021-1022` and `im/read.go:730`, `im/invoke.go:739-748` (every ACL / fabric-sensitive gate bypasses on `fabricIndex==0`).

**Claim:** A datagram with `SessionID==0` is unsecured (no PASE/CASE key — the pre-handshake channel). `decryptIfNeeded` returns its body unauthenticated (`receive.go:316-322`), and a Common-vendor IM datagram then routes straight into `handleIMOpcode`, which decodes and dispatches it. Its fabric resolves to 0, so `HandleReadRequest`/`HandleWriteRequest`/`HandleInvokeRequest` take the fabric-0 branch that is meant for the commissioning PASE channel and skip the ACL check, the fabric-sensitive filter and the fabric-scoped-list filter entirely. Concretely: any host on the LAN sends an unencrypted `ReadRequest` with a wildcard path and SessionID=0 and receives the full attribute tree unfiltered; or an unencrypted `InvokeRequest` of a non-fabric-scoped command (OnOff.Toggle, Identify, LevelControl.MoveToLevel) and the command runs with no access check. `TestDispatch_IMReadRoutes` (`bridge/receive_test.go:288-299`) uses `buildHeader(0, 5)` and asserts the read is routed and processed, so the behaviour is intended, not accidental. (Fabric-scoped invokes and AddNOC/CSR are still blocked — fabric-scoped commands answer UnsupportedAccess at `invoke.go:747`, and AddNOC/CSR require an armed fail-safe which an unsecured channel never has — so the commissioning path itself is not opened; the exposure is unauthenticated reads and non-fabric-scoped control.)

**Reference:** matter.js marks the Interaction Model protocol handler `requiresSecureSession = true` (`packages/node/src/node/server/InteractionServer.ts:161`), and `ExchangeManager` drops any inbound message whose handler's `requiresSecureSession` does not match `session.isSecure` (`packages/protocol/src/protocol/ExchangeManager.ts:393-402,407-411`) — an UnsecuredSession is not secure, so IM is never dispatched over it; only the SecureChannel handler (`requiresSecureSession = undefined`, PASE/CASE) runs there. connectedhomeip dispatches an unsecured session only through `SessionManager::UnauthenticatedMessageDispatch` (`6170af84:src/transport/SessionManager.cpp:807-859`), which serves the handshake; the IM engine runs on secure sessions.

**Fix:** Add an unsecured-session reject to the IM gate: in `handleIMOpcode` (or `classifyIMOpcode`, passing the session security), when the message is not over a secure session (SessionID==0 / `message.SessionUnsecured` and not a group session) drop it without dispatch, exactly as matter.js's `requiresSecureSession` mismatch does — the fabric-0 bypass must be reachable only from a real PASE/CASE-adopted session, never from raw unsecured traffic.

**Confidence:** confirmed by reading both sides.

## W2-sec-02 — medium — an AddNOC-adopted PASE session keeps its implicit Administer grant after CommissioningComplete

**Where:** `bridge/commissioning_window.go:1109-1124` (`EndCommissioning` — "neither evicts PASE sessions nor touches the fail-safe"), wired as the CommissioningComplete hook at `bridge/receive.go:992` (`gc.SetOnCommissioned(w.EndCommissioning)`); `node/node.go:664-673` (`commissioningCompleted` → `failSafeCommitted`, no PASE close); `secure/operational/manager.go:1018-1031` (`ClosePASESessions` exists but has no non-test caller in the tree).

**Claim:** On a successful CommissioningComplete the only session action is `EndCommissioning`, which closes the commissioning window but explicitly does not clear the PASE session. The PASE session was adopted onto the new fabric by AddNOC (`bridge/receive_dispatch.go:910` `AdoptFabricIndex`) and is still marked PASE, so `resolveSessionPASE` keeps returning true and every later Read/Write/Invoke over that channel takes the implicit-Administer PASE bypass (`im/fabric_context.go:144-149`, consumed in all three IM gates). The session therefore retains full Administer on the commissioned fabric, outside the ACL, until the idle reaper eventually evicts it. `notes/parity/matter_behaviour_findings.md:306` records this as FIXED by a daemon CommissioningComplete hook that closes PASE after a 100 ms grace, but no such closer is wired on the current CommissioningComplete path (grep finds no `ClosePASESessions()` caller, and `RevokeWindow` — the only PASE-closing path — is not reached by CommissioningComplete).

**Reference:** matter.js `completeCommission` performs the §11.10.6.6 steps: disarm the fail-safe, close the window, then **clear the PASE session** — `await this.closePaseSession({ cause: new FailsafeExpiredError() })` (`packages/protocol/src/common/FailsafeContext.ts:131-146`), invoked from `GeneralCommissioningServer.commissioningComplete` → `failsafeContext.completeCommission()` (`packages/node/src/behaviors/general-commissioning/GeneralCommissioningServer.ts:246`). Spec §11.10.6.6 step 4: the Secure Session Context of any PASE session still established SHALL be cleared.

**Fix:** Close the fabric-0 PASE session(s) on CommissioningComplete, as `RevokeWindow` already does for the window-revoke path — route `EndCommissioning` (or the node's `commissioningCompleted`) through `ClosePASESessions` (with the same deferred-after-response grace the RemoveFabric path uses so the CommissioningCompleteResponse still ships).

**Confidence:** plausible — the CommissioningComplete path and `EndCommissioning` were read on this side and `completeCommission` on matter.js's; I did not exhaustively trace every `failSafeParticipant.OnCommissioningComplete` implementation to rule out a PASE close hidden there, but none of the ones read closes PASE and the register's documented hook is absent.

## W2-sec-03 — low — an operational session with no fabric resolver and no ACL lister resolves to fabric 0 and is served as commissioning traffic

**Where:** `bridge/subscribe.go:1511-1545` (`resolveSessionFabric`): when the lookup does not implement `SessionFabricResolver` **and** `aclLister == nil`, it returns 0 rather than `FabricIndexUnresolvable`.

**Claim:** For a half-wired bridge (session lookup without `WithFabricResolver`, and no `AttachACLLister`), a CASE session's fabric resolves to 0, so every IM gate treats it as the commissioning channel and grants implicit Administer — full reads/writes/invokes with no access check. The in-code comment argues this is harmless because "CheckACL denies everything operational anyway", but that reasoning only holds when the fabric resolves to non-zero; forcing it to 0 takes the PASE bypass before CheckACL is consulted. The production node wiring always attaches both the resolver (`node/security.go:399-404`) and the ACL lister (`node/node.go:278`), so this is a defense-in-depth gap on a misconfigured host, not a live exposure — the same shape as W1-sec-01.

**Reference:** matter.js never treats an operational (CASE) session as the implicit-PASE commissioning subject — the implicit Administer grant is keyed strictly on `authMode === Pase && isCommissioning` (`packages/protocol/src/interaction/FabricAccessControl.ts:189-191`), never on a missing fabric index.

**Fix:** Return `endpointpkg.FabricIndexUnresolvable` for an unresolvable session whenever the lookup carries no working fabric resolver, independent of whether an ACL lister is attached (the `acl != nil` branch at `:1538` should be unconditional), so a session whose fabric cannot be named is denied rather than waved through as fabric 0.

**Confidence:** confirmed by reading both sides.

## W2-sec-04 — low — ICD RegisterClient re-registration is authorized by VerificationKey compared with `bytes.Equal` rather than in constant time

**Where:** `cluster/core/icd_management.go:1110-1121` (`assertMayModify`): `!bytes.Equal(*verificationKey, stored)`.

**Claim:** A non-Administer caller that modifies or unregisters an existing ICD client proves possession of the stored 16-byte verification key; the comparison is `bytes.Equal`, which is not constant-time, so the match is data-dependent in timing. The key is a shared secret gating who may rewrite another registration's monitored subject / check-in node, so a timing side channel on it weakens that gate. Low because the attacker must already hold a fabric and an operational session, the key is 16 bytes, and matter.js itself does not document a constant-time requirement here.

**Reference:** matter.js `IcdManagementServer` compares the verification key with a plain equality (`packages/node/src/behaviors/icd-management/IcdManagementServer.ts`, `checkInKey` equality); spec §9.17.7 requires the key to match but names no timing property. This is a hardening beyond the references rather than a parity gap.

**Fix:** Compare with `crypto/subtle.ConstantTimeCompare` (guard the length first) — the repo already uses constant-time compares for the PASE cA and resumption MIC (W1 "Checked and sound").

**Confidence:** confirmed by reading this side; matter.js read confirms plain equality (so this is an "ahead of matter.js" hardening, not a divergence bug).

## W2-sec-05 — low — group reception replay windows are keyed by the raw epoch key and never evicted

**Where:** `groups/decode.go:286-301` (`receptionWindow`): `m.reception[hex(key)][source]`, a map keyed on the hex of the group epoch key and the source node id, created on first use and never deleted.

**Claim:** Each (epoch key, source node id) pair gets a persistent `mrp.Window`; the map grows for the daemon's whole uptime — one entry per distinct source node id seen under each group key, and the entries are not dropped when a key set is removed (`handleKeySetRemove`) or a fabric is forgotten. A node on a joined multicast group can enumerate source node ids (the source id is attacker-chosen on the wire for an authenticated group sender, but a key holder is the only one who can author accepted frames), so the growth is bounded by legitimate senders in practice; the concern is the unbounded map plus holding the raw epoch key bytes as a live map key (hex-encoded) for the process lifetime. Low: not network-trivial to blow up (requires valid group-key-authenticated frames) and no trust decision depends on it.

**Reference:** matter.js keys its group reception state on the operational group session and tears it down with the group session / fabric (`packages/protocol/src/session/SessionManager.ts` group-session lifecycle); the window does not outlive the key.

**Fix:** Drop the per-key reception windows when the key set is removed or the fabric is forgotten (`handleKeySetRemove`, `ForgetFabric`, `RemoveGroupKeysByFabric`), and avoid holding the epoch key as the map key (hash it, or key on fabric+keyset id).

**Confidence:** plausible — read on this side; the matter.js lifetime was inferred from the session-scoped reception state, not read line-by-line at the pin.

## W2-sec-06 — note — AddTrustedRootCertificate and AddNOC fail-safe guard skips when the armed-checker is nil

**Where:** `cluster/core/operational_credentials.go:1601-1607` (AddNOC), `:2270-2276` (AddTrustedRootCertificate), `:1459-1465` (CSRRequest): each guard is `if checkArmed != nil && !checkArmed() { return FailsafeRequired }` — a nil `isFailSafeArmed` skips the check.

**Claim:** When `OpcredsConfig.IsFailSafeArmed` is not wired the fail-safe-armed precondition is silently not enforced, so AddNOC / AddTrustedRootCertificate / CSRRequest would run outside any fail-safe. The production wiring always supplies it (`node/root.go:200`, `node/commissioning.go:78`), and these commands are additionally gated by W2-sec-01's secure-session requirement once that is closed, so this is a half-wired-only gap, consistent with the bridge's documented "noop port" philosophy. Noted, not a live exposure.

**Reference:** connectedhomeip makes the check unconditional — `VerifyOrExit(failSafeContext.IsFailSafeArmed(...), errorStatus = Status::FailsafeRequired)` at `6170af84:src/app/clusters/operational-credentials-server/OperationalCredentialsCluster.cpp:341,472,640`; matter.js reaches it through the `failsafeContext` getter's `assertFailsafeArmed()` (`packages/protocol/src/protocol/DeviceCommissioner.ts:97-100`), which cannot be bypassed.

**Fix:** If the project wants these to fail closed when unwired, treat a nil `isFailSafeArmed` as "not armed" (return FailsafeRequired); otherwise record the skip in `by_design.md` as a deliberate test-seam, as the inline comment already half-states.

**Confidence:** confirmed by reading both sides.
