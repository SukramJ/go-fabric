    Roadmap¶

    Set by the owner on 2026-10-17, at v0.6.0, after the module's node had been paired and driven by Apple Home and by Home Assistant's Matter server (both on the reference bridge and OpenCCU-Loom). This page is the one place where the order of the remaining work is written down: what each milestone contains, roughly how it is phased, what it is worth and to whom, and when it counts as closed. The detail of a phase lives in its own document, written when the phase is next (see How a phase is planned).

    The goal¶

    Complete Matter 1.6.1, wherever matter.js implements it. matter.js is the gold standard (CLAUDE.md); the measure of "complete" is therefore its HEAD, not the specification text: every cluster, device type, protocol feature and behaviour matter.js has, this module has — semantically, with the same defaults, the same constraints and the same wire shape — and nothing it lacks is invented here unless a connectedhomeip reference exists, as the parity contract already allows (DiagnosticLogs, FanControl coupling). A generated matter.js stub counts as an implementation: it is served here by the generated default server (ADR 0017), which is exactly as much as matter.js offers for it.

    Beyond the standard: the embedding layer. matter.js is the gold standard; this module is meant to be the diamond one — not a larger protocol surface, but a smaller distance between a host's device model and a paired, working Matter node. The consumers that set that bar:

    Consumer State What it needs from this module
    OpenCCU-Loom in production; today imports 20 packages of this module directly a complete node/ + device/ + contract/ surface so that a bridge needs nothing below it; depth in the clusters HomeMatic devices map to (Switch, Thermostat, DoorLock, WindowCovering)
    go-ha-matter-bridge (working name; planned separately) not started; its concept is written when milestone 4 is due the declarative device kit, the in-process test pair, the adapter module below
    the go-*2mqtt family (daikin, homeconnect, mtec, unifi, zendure) via a shared adapter module (working name go-hamatter: go-hamqtt's Home-Assistant vocabulary → Matter device types; lives outside this module, so contract/ stays stdlib-only) not started the same device kit; energy and appliance device types, which already exist
    examples/reference-controller and a host acting as commissioner shipped, controller stages 1–6b the field features (milestone 1), ICD peers and the rest of OTA push (milestone 5)

    Priority follows from that table: a feature a consumer uses comes before one none uses, and both come before completeness for its own sake.

    How to read this page¶

    • A milestone closes a topic area completely; it is not a sprint. One minor version per milestone (v0.7.0 is milestone 1), patch versions for the waves inside it. The v1.0.0 cut is the owner's call and is not scheduled here; the 0.x series continues until then, and the freeze of device/, node/ and controller/ stays bound to that cut.
    • Phases continue the numbering of the concepts (concept v3 ends at phase 13). A phase is one to three implementation waves, one pull request per wave (one PR per wave).
    • Definition of done is the same three pillars for every milestone, and a milestone is not closed while one is missing:
      1. the chip certification families the milestone names run green in the harness (make chiptool-families), or are classified in certifiability.md;
      2. the matter.js test files the milestone names are ported as Go tests and recorded in the test-porting register with its ratchet (milestone 2 creates both);
      3. the rows of matterjs-comparison.md the milestone names move to ✅, or the gap moves to by_design.md with its reasoning.
    • Every milestone opens with a pin check. matter.js HEAD moves while a milestone runs (the checkout is 52 commits past the pin 0ceb202d today); the first wave of each milestone lifts the pin, classifies the snapshot diff and regenerates, as concept v2 phase 6 did. A fact about matter.js quoted in this page is at the pin named in the milestone.

    Baseline (2026-10-17, v0.6.0)¶

    • 118 of the snapshot's 135 clusters served, 79 of its 91 device types generated; the matter.js servers with hand-written logic number 25 (≥150 lines) and their depth here varies from a full port (ColorControl, LevelControl, WindowCovering, OnOff, OTA) to none (Switch: the generated definition and the wire type only, against SwitchServer.ts 486 lines and a 3 527-line test).
    • Controller role stages 1–6b landed; Joint Fabric (6c) deferred by decision (ADR 0020).
    • Concept v3 phases 11–13 open: crypto.Signer, window-open from the reference controller, the DCL snapshot and BLE commissioning (ADR 0024) — none of it in the tree yet.
    • Verified ecosystems: Apple Home, Home Assistant (owner, 2026-10-17); Google Home and Alexa await the owner at the device (ecosystem observations).
    • matter.js's own tests, the proof for devices nobody has on the bench: 209 *Test.ts under packages/node/test (54 of them behaviour tests in 36 cluster directories, 49 node-level), 114 under packages/protocol/test, 68 certification cases under support/chip-testing/test/cert. None of them is ported as such; the module's parity tests were written from the servers, not from these files.

    Milestone 4: The embedding layer¶

    Detail: written when milestone 3 is closed, together with the concept of the go-ha-matter-bridge and the adapter module, because the three shape each other.

    Phase Content Proof
    20 the node/ facade complete: everything loom reaches below it today (bridge, store, secure/*, mdns, im) is reachable through node/, device/ and contract/, or is documented as an advanced seam; the declarative device kit — a bridged device from a device type, its values and its command handlers in one declaration, with attribute change propagation, transitions and the device-type validator behind it; an apidiff guard from this milestone on, so that a break is announced before it ships loom's import list shrinks to the facade; the reference bridge is rewritten on the kit
    21 observability and persistence as ports: slog attribute conventions, a metrics hook, the diagnostic event ring; the Store seam proved by a second implementation (in-memory, for tests and small daemons); hardening a daemon in the field needs (session and subscription limits documented, PASE attempt limit after §5.5, fuzz targets for the controller decoders) the persistence and concurrency guides describe the ports; make fuzz covers the new targets
    22 packaging and the cookbook: container image and systemd unit for the reference apps, arm64, the "embed in a daemon" guide written against a go-*2mqtt project; the concept documents of the go-ha-matter-bridge and the adapter module a 2mqtt daemon exposes one device type end to end on the kit

    Value. The diamond-standard claim lives here, and it is a claim about embedding and operation, not about Matter semantics: ahead of matter.js in embedding and operation, equal in semantics (owner, 2026-10-19). matter.js asks a host to learn behaviours, agents and transactions; this module should ask for a device type and a handful of callbacks, and ship as one static binary with a small footprint. On the wire it is a port of matter.js and can be as correct as its source, not more; the ecosystem exceptions stay matter.js's. Consumers: every one; the HA bridge and the 2mqtt family cannot start before it.

    Done when. The comparison's "device model" and "runtime" sections have no ◐ left except the behaviour-layer idiom row; loom and one 2mqtt daemon build on the facade alone.

    Standing work, outside the milestones¶

    • Pin lifts open every milestone (above).
    • The chip harness keeps running on every wave that moves the daemon's composition or a FeatureMap; a wave that does not is said so in its report.
    • The findings register takes every gap an audit finds; closing one removes it. Ecosystem findings go to the observations page.
    • Google Home and Alexa runs happen when the owner is at the device; their findings enter the register and may re-order a milestone's phases, not the milestones.
    • Security paths (secure/, commissioning/, ACL, the four hand-written core servers) are reviewed by the strongest model whatever the milestone, as CLAUDE.md assigns them.

    How a phase is planned¶

    A phase gets its detail document when it is next, not before: German, under docs/ while it is current (as concept v3), moved to docs/history/ when its milestone closes. It names the matter.js files at the pin with line ranges, the Go packages it touches, the decisions it needs from the owner (asked as a wizard with a recommendation), the waves with one agent each, and the three pillars it has to show. An architecture decision or a deliberate divergence inside it becomes an ADR or a by_design entry in the same pull request. The adapter module and the go-ha-matter-bridge get their own concept documents in their own repositories, written in milestone 4.
